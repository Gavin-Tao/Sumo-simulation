================================================================
STATE 设计详解
方案A(相位级) vs 方案B(转向级)
+ 堵塞的两种探测法(反应式 / 预测式)
+ 带数字的逐格推演
================================================================

【导读】本文回答三件事:
  1. 到底假设了什么 —— 这决定哪些特征算得出来(很重要)
  2. 堵塞怎么探测:
       【甲】反应式 indicator —— 假设最轻(不需要转向、不需要次序)
       【乙】预测式 servable/blocked —— 需要已知转向 + 已知次序
  3. 同一份排队快照,在方案A和方案B里一格一格算出来,看清两者差别


================================================================
第0部分:假设(Assumptions)—— 先说清楚
================================================================

永远已知 / 可观测(无需任何额外假设):
  - 信号状态(自己控的)
  - 车道上有没有车、排队多长、占有率(检测器)
  - 车型:小车/公交/救护车(→ 映射成优先级等级,不需要知道它要去哪)

"转向"和"次序"是两层【额外】假设,不同特征依赖不同:

  ┌────────────────────────────────┬──────────────────────────────┐
  │ 特征                            │ 需要的额外假设                 │
  ├────────────────────────────────┼──────────────────────────────┤
  │ count / present(每转向几辆)    │ 已知转向(成分)                │
  │ servable / blocked(预测式,法乙)│ 已知转向 + 已知队列次序         │
  │ 反应式 blocked indicator(法甲) │ 都不需要! 只需"绿了走没走"      │
  └────────────────────────────────┴──────────────────────────────┘

  SUMO 仿真里:转向(来自 route)+ 次序(来自车辆位置)都白拿,法乙能用。
  真实部署里:已知"次序"比已知"转向"更强;法甲(反应式)最可部署。

  注意:方案B 按【转向】组织槽位 → 天生需要"已知转向"。
        方案A 按【相位】组织 → 既可"按转向归属"(需转向),
              也可"按相位放绿的车道聚合"(连转向都不需要,配法甲最自然)。

优先级等级(BNF runtime 映射): L1=小车(权1) L3=公交(权3) L5=救护车(权5)
  L2、L4 本路口未定义(演示"子集"情形)。
  STATE 里只出现【等级】,从不出现车型 → 换一套 车型→等级 映射零样本可用(BNF迁移)。

================================================================
第2部分:堵塞探测【甲】反应式 indicator(假设最轻)
================================================================

定义(每条车道 ℓ、每个控制步):
  blocked[ℓ] = ( ℓ此刻绿 ) 且 ( ℓ上有车 ) 且 ( 队首没在放行 )  → 记 1
  - "没在放行" = 绿灯持续超过起步阈值(避开1~2s起步)后队首仍不动 / 车数不减
  - 不需要知道队首要去哪,只看"本该走却没走"

带记忆(因为大多数道大多数时候是红的):
  - 绿时:用新鲜观测刷新 blocked[ℓ]
  - 红时:保持上次值,并记 staleness[ℓ](多久没刷新 → 这个判断有多旧)
配优先级:再带上该道排队的【优先级成分】(按车型识别,不需转向)
  → "这条道被堵,而且上面有救护车"

时间线示例(只看 N1):
  t0  NS直行 刚绿:起步后 v1(左)不动 → N1 绿+有车+没走 → blocked[N1]=1
                  N2 的 v4,v5 正常走 → blocked[N2]=0
  t1  仍堵:blocked[N1]=1
  ── agent 切到 N全绿 ──
  t2  左转也绿:v1 走掉 → N1 开始放行 → blocked[N1]=0,v2,v3 跟着走
  (假如 v1 走后 v2 又是左转:下一步又观测到绿+没走 → blocked[N1]=1
   → "后面的车又挡住"自动被抓到,不需要额外逻辑)

性质(诚实):
  - 【反应式】:只能在给了绿之后才知道;只对"当前/刚才那个相位"的车道新鲜,
    其它相位是红的、无新观测 → 要靠记忆 + staleness 带着用。是"后视镜"不是"车灯"。
  - 【不分原因】:绿了没走可能是转向堵、也可能是下游溢出/抛锚 → 一网打尽但说不清为何。
  - 【裸bit无优先级】:必须配"该道优先级成分"才知道堵着的是不是救护车。
  - 最大优点:假设最轻、最可部署,且解决了"没收益是因为被堵 vs 因为没需求"的归因。


================================================================
第3部分:堵塞探测【乙】预测式 servable/blocked(需转向+次序)
================================================================

定义(从当前队列快照 + 每个相位放行的转向,前向算,不是事后):
  servable = 选这个相位,从队首往后【连续被放行】的那段前缀里的车数(真能走)
  blocked  = 转向被放行、但排在某个"不被放行"的车后面 → 放不出的车数
  max_awt  = 该格涉及车辆的最大累计等待

  规则:对相位放行涉及的每条车道,从队首数连续"转向被放行"的车;
        遇到第一辆"转向不被放行"的车就截断,截断点之后的同向车 = blocked。


================================================================
第4部分:方案A(相位级)逐格算   —— 用【乙】预测式
================================================================

张量:8相位 × 5等级 × [servable, blocked, max_awt]

── 行【NS直行】放行{N直,S直} ──
  N1: 队首 v1=左 → 不放 → 立刻截断 → N1 servable=0;v2,v3(直)被堵
  N2: v4,v5(直) → servable      S1: v6,v7(直) → servable      S2: 左→不碰
  L1(小车): present={v2,v4,v5,v6}=4 → servable={v4,v5,v6}=3, blocked={v2}=1, max=30
  L3(公交): servable={v7}=1, blocked=0, max=16
  L5(救护): servable=0, blocked={v3}=1, max=12   ★救护车被堵★

     NS直行:  L1[serv3,blk1,max30]  L3[serv1,blk0,max16]  L5[serv0,blk1,max12]★

── 行【NS左转】放行{N左,S左} ──
  N1: v1(左)队首→servable;   S2: v8(左)→servable
  L1: present={v1,v8}=2 → servable=2, blocked=0, max=22

     NS左转:  L1[serv2,blk0,max22]

── 行【N全绿】放行{N左,N直,N右} ── ← 看这里!
  N1: v1(左)被放→走 → v2,v3 跟着解锁 → N1 全 servable
  N2: v4,v5 → servable
  L1: present={v1,v2,v4,v5}=4 → servable=4, blocked=0, max=30
  L5: servable={v3}=1, blocked=0, max=12   ★同一辆救护车,这里能走了!★

     N全绿:   L1[serv4,blk0,max30]  L5[serv1,blk0,max12]★

┌──────────────────────────────────────────────────────────┐
│ 同一辆救护车 v3,在 A 的两行里:                            │
│   NS直行 → L5 [serv=0, blk=1]  (被堵)                      │
│   N全绿  → L5 [serv=1, blk=0]  (解堵)                      │
│ → A"每相位一行",把"换全绿能解堵"直接算了出来               │
└──────────────────────────────────────────────────────────┘

── 若改用【甲】反应式:A 的每相位行不再放 servable/blocked,
   而是放"该相位放绿的车道的 blocked_belief 聚合 + 这些道的优先级成分 + staleness"。
   注意此时只有【当前相位】的 belief 新鲜,其余为上次观测的旧值。

三方案共用的其余 block:
  BNF描述子(5×[present,weight]): L1[1,1] L2[0,0] L3[1,3] L4[0,0] L5[1,5]
  相位上下文(8×[active,is_current,since_green]):
     NS直行[1,0,45] WE直行[1,1,0] NS左转[1,0,38] WE左转[1,0,60]
     N全绿[1,0,90] S全绿[1,0,90] W全绿[0,0,0] E全绿[0,0,0](mask)
     全局 current_phase_elapsed=15
  全局几何: 进口数=4, 总车道数=8, has_shared_lane=1

喂动作:每相位拼成一行 → 共享 scorer → 8分数 → phase_active mask → 选最大


================================================================
第5部分:方案B(12槽位/转向级)逐格算   —— 用【乙】预测式
================================================================

张量:12转向槽({N,E,S,W}×{左,直,右}) × 5等级 × [servable, blocked, max_awt]
(按转向归属 → 必须已知转向;servable 按"该转向自己的标准绿灯"算)

── 槽【N-直】 车:v2,v3(N1) v4,v5(N2) ──
  直行绿/左转红:N1 的 v2,v3 在左转 v1 后被堵;N2 的 v4,v5 servable
  L1: serv={v4,v5}=2, blk={v2}=1, max=30
  L5: serv=0, blk={v3}=1, max=12   ★救护车被堵(B 也能表示)★
── 槽【N-左】 v1 ── L1: serv=1, blk=0, max=20
── 槽【S-直】 v6,v7 ── L1: serv=1,blk0,max18 ; L3: serv=1,blk0,max16
── 槽【S-左】 v8 ── L1: serv=1, blk=0, max=22
其余槽 0 / 不存在的 mask

喂动作:12槽是按【转向】的,动作是8个相位 → 用"模板→转向"结构把12槽
        组合成8个相位分数(FRAP 的 phase-competition 做法)。


================================================================
第6部分:关键差别(用数字看)—— "全绿能放几辆?"
================================================================

真值(A 的 N全绿 行直接给): servable L1=4 + L5=1 = 5 辆(v1..v5 全走)

B 怎么估: N全绿 放行{N-直,N-左},把两个槽 servable 相加:
     N-直.serv=2(L1)   N-左.serv=1(L1)   天真相加 = 3   ❌
     真值 = 5,差的 2 辆 = v2(直)+v3(救护)
     原因:"放 N-左 → 队首左转 v1 走掉 → N-直 被堵的 v2,v3 解锁"
          这是【非线性交互】,B 的 per-转向 servable 线性相加拼不出来,要 agent 自己学。

┌─────────────────────────────────────────────────────────────┐
│ 1. "此刻谁被堵": A 能, B 也能。                               │
│ 2. "换相位(全绿)能否解堵"这个非线性后果:                     │
│      A 按相位算→直接写在 N全绿 行(serv=5);  B 按转向算→看不到,要学│
│ 3. "同车道哪辆左转堵了哪辆直行": A、B 都辨识不了                │
│      (聚合掉了车道身份);只有"车道token+Transformer"能完全辨识 │
└─────────────────────────────────────────────────────────────┘

第7部分:两个维度的对比(组织方式 × 堵塞探测)
================================================================

维度一:状态组织   A(相位级) vs B(转向级)
  ┌──────────────────┬───────────┬───────────────┐
  │                  │ A 相位级   │ B 转向级       │
  ├──────────────────┼───────────┼───────────────┤
  │ 与8相位动作对齐   │ ✅直接     │ ❌要学12→8     │
  │ "此刻谁被堵"      │ ✅         │ ✅             │
  │ "全绿能否解堵"    │ ✅直接     │ ◯ 要agent学    │
  │ 同车道耦合辨识    │ ❌         │ ❌             │
  │ 分辨率           │ 相位(粗)  │ 转向(细)      │
  │ 风格             │ CityLight  │ FRAP           │
  └──────────────────┴───────────┴───────────────┘

维度二:堵塞探测   甲(反应式) vs 乙(预测式)
  ┌──────────────────┬─────────────────┬──────────────────┐
  │                  │ 甲 反应式        │ 乙 预测式 servable │
  ├──────────────────┼─────────────────┼──────────────────┤
  │ 额外假设         │ 无(绿了走没走)  │ 已知转向+次序     │
  │ 能预判候选相位吗  │ ❌只事后/当前相位│ ✅当前快照对8相位 │
  │ 区分原因         │ ❌混(连spill都抓)│ ✅精确到转向      │
  │ 部署现实性       │ ✅最现实         │ 仿真/CAV          │
  │ 是否需记忆       │ 需(staleness)   │ 不需(每步重算)   │
  └──────────────────┴─────────────────┴──────────────────┘

两维正交:A或B 都可配 甲或乙(B需已知转向;A按车道聚合时连转向都不需要,配甲最自然)。


================================================================
第8部分:一句话总结 + 选型
================================================================

A(CityLight式): 按相位组织,把"每个动作的后果(含解堵)"预先算进 state;
                与动作对齐、解堵直接可见;但偏预消化、分辨率粗。
B(FRAP式):     按转向组织,报当前事实,让 agent 自己组合;
                分辨率细;但与动作不对齐、解堵交互要学。

甲(反应式indicator): 绿+有车+没走→标记,带记忆+优先级成分;
                假设最轻最可部署;但事后才知、只新鲜于当前相位、不分原因。
乙(预测式servable): 从队列前缀算,能预判8相位、精确;但需已知转向+次序。

选型建议:
  - 你若不想背"已知转向/次序"的假设 → 主线 A + 甲(反应式 indicator):
       state = 各相位放绿车道的[占有/优先级成分 + blocked_belief + staleness]。
  - 你若接受"已知转向+次序"(SUMO白拿,且与你们组CAV线一致)→ A + 乙(servable/blocked),
       blocking 表示最好(还能直接看到全绿解堵)。
  - 最佳做法:在 SUMO 里把"乙"当 oracle 上界,拿"甲 vs 乙"做消融,
       量出"预判能力到底值多少"——甲那侧是真实可部署的方案,这是一条干净的 thesis 消融。
  - B 出局的理由:与动作不对齐 + 解堵非线性要学;但它是合法的 FRAP 式路线,可作对照。

(注:所有 servable/blocked/count 这里用原始计数;实际用时除以车道容量归一化,
 以便一套策略跨不同车道数的路口迁移。)
