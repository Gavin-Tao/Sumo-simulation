# 设计定稿: 上游延伸观测 + 优先级加权汇总特征 (2026-10-27)

针对 PRIORITY_EVIDENCE_2026-10-27.md 查出的两个问题:
- 问题一 (看不见): 受控进口道短于十几秒车程时 (1448436 南进口 22 m, 四个路口最短 10–11 m), 非 RL 路口后面的来车在进入进口道前不在状态里, 优先级没有时间起作用。
- 问题二 (认不得): 每类车各自独立的状态维度, 救护车维度在训练里几乎恒为 0, 网络从未学到; 孪生救护车比孪生小汽车多停 3–6 s, 红灯槽注入救护车的翻转率 18–39% 低于小汽车 50–60%。

原则: 全部是**默认关的新开关**, 旧配置逐位不变; 奖励、统计器、动作集、F1 掩码一律不动; 只改观测类与它的独立重算核对工具。

## 1. 问题二: 优先级加权汇总特征 (obs_priority_agg)

**What.** 每个运动槽在现有 28 维之后加 3 维:

| 维 | 定义 | 归一 |
|---|---|---|
| wcount | Σ_w w · count_w / cap | 直接用 (车道满载小汽车 = 1, 满载救护车 = 5) |
| wqueue | Σ_w w · queue_w / cap | 同上 |
| wawt | Σ_w w · awt_w, awt_w 为该类平均本次访问等待的对数刻度 log1p(s)/log1p(3600) | 直接用 (小汽车等 100 s = 0.56, 救护车等 151 s = 3.07) |

w 取自 priority_source (与奖励同一张表); 111 臂全 1 时三维退化为总计数/总排队/各类对数等待之和, 对车型盲的臂无害。原分类维度保留。
可选开关 obs_priority_agg_scale: log (默认) | linear (awt 用 min(s, 500)/100, 与奖励同形式), 作为消融。

**Why.** 奖励是 −Σ_w w · 平均等待_w / 100, 加权汇总就是奖励在每个槽上的充分统计量; 它只要槽里有车就非零, 每步都在训练, 救护车的贡献沿着小汽车练熟的、单调的方向进入网络 (见 PRIORITY_EVIDENCE §0 第 3 条与对话记录), 而不是落在从未非零过的维度上。

**How.**
- observations.py `PriorityMovementObservationFunction`: 新参数 priority_agg: bool = False, priority_agg_scale: str = "log"; 在每槽循环末尾 (slot_min_green 之后) 追加 3 维; observation_space 维数同步 (28 → 31/槽, 336 → 372)。
- exp_params.obs_kwargs_from_cfg 透传 obs_priority_agg / obs_priority_agg_scale。
- state_reward_debug.Ref.expected_state 同步加这 3 维的独立重算 (验证链要求: 差 ≤ 1e-5 才算实现正确)。
- 其他 (train.py, ckpt_env, eval 工具) 通过 obs_kwargs_from_cfg 自动适配, 不改。

## 2. 问题一: 上游延伸观测 (obs_upstream_ext)

**What.** 对每个路口的每条受控进口道, 从停车线往上游量一个固定的观察距离 D (默认 120 m, 约 10–15 s 车程): 进口道自身够长的, 延伸段为空; 不够长的, 沿前驱车道跨过非 RL 节点继续, 直到累计 D 或碰到另一个 RL 路口为止 (RL 路口的进口道不纳入, 那是它自己的状态)。延伸段上的车按路线判断会进入本进口的哪个运动槽 (与现在给进口道上的车分槽同一规则: (进口边, 下一条边) → 槽), 每槽加 12 维 "在途" 特征:

| 维 | 定义 | 归一 |
|---|---|---|
| ext_count_w (5 维, 每优先级 1) | 延伸段上将进入本槽的该类车数 | / N_ref (默认 10) |
| ext_prox_w (5 维) | 该类最近一辆的接近度 1 − d/D, d 为到停车线的沿路距离; 没有车 = 0 | 0–1 |
| ext_wcount (1 维) | Σ_w w · ext_count_w | / N_ref |
| ext_wprox (1 维) | Σ_w w · ext_prox_w / w_max | 0–1 |

**故意不放**延伸段上的等待、排队、速度: 车在非 RL 让行口等了多久是上游的事, 本路口控制不了也不该为此被奖惩 (10-26 修正去掉的 "继承等待" 不能从这里回来); 本路口需要的只是 "有谁、多近、要来"。奖励与 visit 统计器完全不变, 车进入受控进口道后才按原口径计等待。

**Why.** 等价于在停车线上游 D 米装一组按运动分类的计数检测器 (SCOOT 的检测器摆法); RESCO 真实路网的工作对 < 15 m 的短车道同样把前驱车道并入状态 (arXiv 2309.09881); 救护车/公交的位置特征是 EMVLight 一类 EV 优先工作的标准做法。用接近度而不是距离, 是为了让 "没有车" 与 "车在很远" 都是 0、"车到门口" 是 1, 单调且无歧义。

**How.**
- 建表 (reset 时一次): 用 sumolib 读 net_file (obs_kwargs_from_cfg 传入路径), 对每条受控车道递归取前驱车道 (lane.getIncoming), 节点类型为 traffic_light 且 id 在 RL 路口集合里就停, 否则继续, 记每条延伸车道的 "车道末端到停车线的沿路距离" 偏移; 累计超过 D 的分支截断; 延伸车道与任何 RL 进口道互斥 (不重复计数)。
- 每步: 扫延伸车道上的车, 用路线找到本进口边在路线中的位置 (不在 → 不计), 槽 = by_edges[(进口边, 其后一条边)]; d = 偏移 + (车道长 − lanePos)。
- 参数: obs_upstream_ext: bool = False, obs_upstream_dist: 120, obs_upstream_nref: 10。维数 +12/槽 (336 → 480; 与问题二同开 → 516)。
- state_reward_debug.Ref 同步独立重算 (自己建延伸表, 不读观测类的表), 并新增一项静态审计: 每条延伸车道的偏移、是否跨过了 RL 路口、与进口道是否重叠。
- 延伸段的车不进奖励、不进统计器、不进 lane_occ。

## 3. 部署层兜底 (与训练无关, 可先行)

救护车抢占掩码 (已零重训验证: 孪生救护车 6.59 → 0.88 s/visit, 其他小汽车略好): 触发条件在实现时同时支持两种来源: (a) 受控进口道上的优先级 5 计数 (现在的探针); (b) 延伸段 (或沿路线 300 m 内) 的在途救护车。规则只在救护车出现时干预, 不碰用户否决的 "空槽绿灯掩码"。作为评估/部署选项 (eval_preempt_amb: false 默认关), 报告每集强制次数。

## 5. 风险与取舍

- 维数 336 → 516, 学习可能变慢: 先看 A (372 维) 是否已足够解决问题二, B/C 再上。
- 延伸表依赖路网拓扑与车辆路线 (与现有分槽同一假设: 车辆意图可知); 真实部署对应 V2I/GPS 上报或上游检测器, 论文里写明。
- 加权汇总的 log/linear 两种刻度留开关; 若 A 的 Tier 3 翻转率升了但 Tier 2 没改善, 问题在检测范围 (去做 B), 而不是再调刻度。
- 不做: 并路口簇、改车流、改奖励、加头车运动特征 (另有记录, 低优先级)。

## 6. 决策时掩码: 最长等待 + 救护车抢占 (与 F1 同一机制)

统一函数 `decision_mask(env, ts, state)` 返回允许的标准动作集合, 依次套: 静态菜单掩码 → F1 最短绿 (未满足时只留当前相位, 物理约束, 最高优先) → 救护车抢占 → 最长等待 → 剩下的交给策略按 Q 选。三处同用: 训练选动作、回放池里的 next_mask (TD 目标, 与 F1 同)、训练中评估分支 (现为静态掩码, 要改) 与 ckpt_env.act (评估工具自动一致)。现有 train.py `_dyn_mask_std` 扩成这个函数。

### 6.1 最长等待掩码 (mask_max_wait, 秒; 默认 0 = 关; 训练与评估都开)

- 规则: 对每个真实槽, 若 当前红灯 且 有车排队 且 槽内本次访问**最大**等待 ≥ W_max, 记为饿着的槽; 存在时取等待最长的 k*, 可选动作 = 放行 k* 的相位 (∩ 静态掩码); 不存在时不干预。等待读 env.visit_tracker 的最大值 (不用平均: 头车等 70 s、后车刚到时平均只有 16 s 也该触发)。
- 为什么: 直接针对锁死根因 (罕见状态 Q 无差别/外推错 + 贪心无随机性 → 一个方向被无限期晾着); 只在已经有人等了 W_max 后介入, 不禁止提前绿灯、不干预正常长绿 (零重训探针: 正常集 0 次干预, 两个自然锁死集各改 1–4 次决策即解开); 同时给出可写进论文的保证 "任何有排队的方向红灯不超过 W_max + 最短绿", 也回应 659802 南进口一类的公平性质疑。下一场景 (每集 50 辆救护车) 里权重 5 的长等待会更常见, 这条还顺带封住奖励尾巴 (−50 截断那种样本)。
- W_max: 先用 best 检查点在 10 种子上扫 45 / 60 / 90 s 看干预次数与指标, 再定进训练; 预期 60 s。
- 风险: 太小会打断合理长绿 (主路常绿、支路刚来一辆车)。

### 6.2 救护车抢占掩码 (eval_preempt_amb: bool; 默认关; **只在评估/部署开, 训练关**)

- 规则: 某槽有救护车 (优先级 5 计数 > 0; 上游延伸做好后也含延伸段上的在途救护车) 时: 该槽红灯 → 可选动作 = 放行它的相位; 该槽已绿 → 可选动作 = 保持放行它的相位 (不许切走, 这一半只有在有预见时间时才有意义)。多辆时取等待最长 / 最近的。只对救护车, 公交优先留给学习。F1 仍优先。
- 为什么: 现状策略不认识救护车 (红灯槽注入救护车翻转 18–39%); 规则不依赖学习 (探针: 孪生救护车 6.59 → 0.88 s/visit, 其他小汽车 1.296 → 1.243, 每集强制 64 次); 它是论文必须有的 "规则抢占" 基线, 学到的优先级要和它比, 报三列: 只学习 / 学习 + 规则 / 111 + 规则。
- 训练时关的原因: A/C 臂要检验策略有没有学会救护车优先, 训练开着规则就分不清是学的还是规则给的。
- 报告: 每集强制改动次数、救护车孪生停车与首绿、其他小汽车的变化。
- 风险: 救护车连续到达时相位被反复强制 (36 辆/集时 64 次, 可接受); 共享车道上救护车排在小汽车后面时, 放行它也会先放前车 (物理限制)。

### 6.3 不做的两项

- 切换代价重训 (针对 1448442 / cluster_21620852 的最短绿轮转, 每集切 300 次、27–33% 步数给空槽绿灯): 效率问题, 上限全网约 10%, 新旧一样, 与优先级主张无关; 零重训加约束无效 (最短绿 10/15 s、屏蔽部分相位都更差)。留作以后 "周期结构" 的独立消融 (奖励加切换代价 c ∈ {0.01, 0.02, 0.05} 或去部分放行相位重训), 不插在优先级这条线前面。
- 389281 的两个空进口相位 (a5, a2, 两次全网连锁锁死的起点): 不删 (路网跨场景共用), 由 6.1 兜住。

## 7. 下一场景 (18h 基底 + 每集 50 辆公交 + 50 辆救护车, 同一路线集, 531 对 351) 下这四项怎么取舍

- **优先级加权汇总 (§1)**: 从必需降为可选消融。每集 50 辆后两类维度都有足够梯度, 网络能直接学到权重差, 531/351 各自重训也不需要跨类外推; 剩余价值是学习效率与训练分布外的泛化 (原 18h 单救护车、陌生路线)。
- **上游延伸观测 (§2)**: 仍然成立 (物理检测范围, 与车多少无关), 但不是这组对照的前提: 两臂在短进口道路口受同样的封顶, 对照公平, 只是优先级的绝对效果被低估。先跑主对照, 再加一臂带延伸看提升; 论文至少写明短进口道局限。
- **最长等待掩码 (§6.1)**: 更需要 (权重 5 的长等待更常见, 封住奖励尾巴与锁死), 训练评估都开。
- **救护车抢占 (§6.2)**: 只作评估基线, 训练关; 50 次抢占/小时对其他车的代价不小, "学到的优先级 vs 规则抢占" 的对比在这个场景里才有看头。

场景本身的设计点 (比上面四项更要紧):
1. **三类车物理参数完全一致, 只有 type id 不同 (用户决定 2026-10-27)。** 现在 SUMO 实际加载的参数 (car 只写了颜色, 其余为 passenger 类默认; bus 写了 vClass=bus 与 12 m; ambulance 写了 vClass=emergency):

| 参数 | car | bus | ambulance |
|---|---|---|---|
| vClass | passenger | bus | emergency |
| 车长 / 车宽 | 5.0 / 1.8 m | 12.0 / 2.5 m | 6.5 / 2.16 m |
| 加速 / 减速 / 紧急减速 | 2.6 / 4.5 / 9.0 m/s² | **1.2** / 4.0 / 7.0 | 2.6 / 4.5 / 9.0 |
| 最高车速 | 55.6 m/s | **27.8 m/s** | 55.6 m/s |
| speedDev (期望速度离散) | **0.1** | 0 | 0 |
| 车类特殊行为 | — | 可用公交专用道 | 可右侧超车、借对向车道、无优先路口可超车 |

   公交一半的加速度与 2.4 倍车长会直接进 "公交停车/延误" (孪生测试里车型盲的 111 臂公交比小汽车多 0.1 s 就是这一项); 救护车的 emergency 类在非 RL 让行口的行为与小汽车不同。下一场景的做法: 三个 vType 都用同一套参数 (建议 passenger 默认: 5 m / 1.8 m, accel 2.6, decel 4.5, maxSpeed 55.6, speedDev 0.1, tau 1.0, 不写 vClass 或三者同一 vClass), 只保留 id 的差别供优先级表与统计器识别; 这样 531 对 351 的差别只剩权重。现有 18h 主结果里的公交数字带着这层动力学差别, 论文报公交对小汽车的差距时要注明; 干净的优先级证据以换车型孪生为准 (同一辆车换 id, 动力学全部抵消)。
   注意: 把 bus 改成 5 m 会改变它占用车道的长度与排放能力, 新场景与旧 18h 公交结果不可直接相比; 这是有意为之, 新场景回答的是 "权重的作用", 不是 "12 米公交的通行"。
2. 同路线集但交错出发 (公交 t、救护车 t + 50 s), 否则同时同路线会前后粘连; 对称设计下 531 的公交指标应镜像 351 的救护车指标, 这本身是一个检验。
3. 路线从小汽车路由抽 (如 36 辆探针的做法, 覆盖 18 个路口), 不用 GTFS 公交线路 (集中在少数主干路口)。
4. 评估沿用换车型孪生 (同一批探针再以小汽车身份跑一遍), 两类的数字都从这里出。
5. 50 辆/h 各占访问量约 1.7% (现公交 4.3%), 可训练; 再多就变成 "多 100 辆高优先级车对全网的代价" 的问题。

实施顺序 (下一场景): 最长等待掩码 + 场景路由 (对称车型、交错出发) + 531/351 两臂 → 评估加抢占基线与孪生对照 → 再决定延伸观测与加权汇总的消融臂。

需要批准后实施; 若先做原 18h 的 A/B/C: 观测类两开关 + 掩码函数 → 重算工具 → 静态审计/快照对等 → 启动。

## 8. 文献对照: 这些设计点别人做了没有

| 设计点 | 本项目现状 → 本文方案 | 文献里的做法 |
|---|---|---|
| 最短绿 | 5 s, F1 决策时掩码 (训练+评估) | 普遍有: Kwesiga 等 2024 用无效动作掩码 (IAM) 约束最短绿/清空相位/相序 [1]; Müller & Sabatelli 2022 用相位图 + 掩码, 含相位专属最短时长 (如 10 s) 与心理规则 (相位 ≥ 6 s, 禁 3→1→3) [2]; 公平控制一文 7 s 最短绿、3 s 黄灯、每 5 s 决策 [3]; RESCO 把黄灯作为环境强加的约束而非动作 [4]; CityFlow 系 (PressLight/CoLight/MPLight) 按公开代码默认以固定 10 s 决策间隔充当最短绿 |
| 最长绿 / 最长红 | 只是名义值 (未执行) → 最长等待掩码 (W_max = 60 s, 训练+评估) | 有先例且常用掩码实现: Kwesiga 2024 IAM 直接含最长绿, 另加 "最长绿前切换且本相位仍排队" 的惩罚 M [1]; Müller 2022 超过相位最长时长时掩码强制离开 [2]; CVLight 执行 40 s 最长绿 [5]; VissimRL 最短 5 / 最长 120 s [6]; CityFlow 系按公开代码默认没有最长绿 (相位可无限保持), 与本项目原状相同。本文用 "最长等待" 而非 "最长绿", 更贴近锁死根因, 也不打断没人等的长绿 |
| 检测范围 / 上游 | 只看受控进口道 (10–373 m, 四个路口 ≤ 11 m) → 跨非 RL 节点上游延伸 120 m, 在途计数 + 接近度 | Kwesiga 2024: 假设 CV, 通信区 800 ft (244 m) 按 25 ft 分格给出公交位置与速度向量 [1]; EMVLight: 每进口一个 "救护车到路口距离" 分量 [7]; RESCO 真实路网上的工作把 < 15 m 的短车道与前驱车道合并进状态与奖励 [8]; CityFlow 系用整条进口道 (合成网 300 m); Müller 2022 逐车道 queue/wait/speed/count, 范围未说明 [2]; 英戈尔施塔特实路口研究假设 70 m 摄像头范围 |
| 优先级车辆的状态表示 | 每槽每优先级独立的 count/queue/awt → 保留并加 Σ w·(count, queue, awt) 汇总 | 多数 RL-TSP 把公交参数放进状态, "有公交时填入, 否则置零" [1 §2.2] —— 与本项目同一结构, 同样面临稀疏; Kwesiga 2024 把公交位置/速度做成单独向量并交给单独的事件触发 TSP 智能体 [1]; EMVLight 用距离向量 [7]。按权重汇总成奖励的充分统计量, 文献里未见, 是本文的新做法 |
| 高优先级样本稀疏 | 每集 1 辆救护车 (已证明学不到) → 每集 50 公交 + 50 救护车 (下一场景) / 加权汇总 | Kwesiga 2024 明确指出公交到达稀疏使单一智能体难以同时学会普通控制与优先, 多项研究靠 **放大公交到达量** 制造样本 (其引文 19, 20, 22, 34), 且对低频公交的泛化与对其他车的代价未见报告; 其自身方案是事件触发的独立 TSP 智能体 [1] |
| 规则抢占 vs 学到的优先 | 奖励加权学习 → 另加救护车抢占掩码作评估基线 (训练关) | 工程实践是规则抢占 (Opticom/GPS, 数百米外触发); Kwesiga 2024 的 TSP 智能体本身就是事件触发 (公交进入通信区才接管), 奖励含 W_bd、W_bv 权重与侧路排队惩罚 [1]; EMVLight 学习 + 距离特征 [7] |
| 对其他车/公平性的约束 | 奖励里没有 (659802 南进口 8.5 s/visit) → 最长等待掩码给出 "红灯 ≤ W_max + 最短绿" 的保证 | Kwesiga 2024 侧路排队超阈值罚 −9999 (N) [1]; 公平性专门目标的工作 [3]; Müller 2022 的心理规则 [2] |
| 评估设计 | best × 10 种子逐秒; 换车型孪生配对 (新) | 多次重复种子是标准 (Kwesiga 10 个种子, 1 h 含 15 min 预热, 报公交延误 / 主线行程时间 / 侧路延误 [1]); 同车换型的配对对照未见报道 |
| 路网 | 真实都柏林 18 个 RL 路口 + 非 RL 节点, 标定车流 | Kwesiga: Vissim 合成双路口 [1]; Müller: Lemgo 单个真实路口 [2]; RESCO: 科隆 / 英戈尔施塔特真实路网 [4][8]; CityFlow 系: 全受控网格 |

### 8.1 与 RESCO 逐行对照 (Ault & Sharon, NeurIPS 2021 Datasets & Benchmarks; 同样建在 SUMO-RL 之上)

| 项目 | RESCO | 本项目现状 | 本文方案 / 差异 |
|---|---|---|---|
| 基础库与仿真 | SUMO + SUMO-RL + Gym 接口 | 同一个 SUMO-RL 分支 (本仓库) | 相同; RESCO 的默认行为可直接类比 |
| 路网 | 科隆 (TAPAS Cologne)、英戈尔施塔特 (InTAS) 真实路网, 各取单路口 / 走廊 / 区域三种任务; **"提取区域内其余路口按优先通行规则控制"** (即含非 RL 让行口) | 都柏林 18 个 RL 路口 + 非 RL 让行口, SCATS/GTFS 标定车流 | 相同类型; RESCO 没有讨论非 RL 路口对观测与奖励的影响 (继承等待、短车道), 本项目 10-26 修正与本文 §2 是对这一点的补充 |
| 状态特征 | 每进口道: 停车排队数、接近中 (未停) 车数、停车车辆总等待、接近车速度和、最大等待、本步到达数、离开数; 用户选子集; 当前相位 | 每运动槽 × 每优先级: count / queue / mean_awt (对数, visit 口径) + is_green + lane_occ + 下游 count/queue + min_green | 粒度不同 (RESCO 按车道、本项目按运动槽 × 车型); RESCO 无车型维度; 本文加 Σw 汇总与在途特征 |
| 检测范围 | 用户在初始化时指定 "有效感知距离"; 对比实验统一 **200 m 半径**; 特征仍按进口道统计 (后续工作指出其真实路网里 < 15 m 的短车道需并入前驱车道 [8]) | 整条受控进口道 (10–373 m), 不越过非 RL 节点 | 本文 §2: 沿路线跨非 RL 节点延伸到 120 m, 在途计数 + 接近度; 与 RESCO 的 "统一半径" 思路一致, 多了按运动槽与按车型 |
| 动作空间 | 非冲突相位组合集合 (按路口给定); **默认每个动作持续 10 s, 需要时前 3 s 为黄灯** (沿用 Ma & Wu) | 8STD 标准相位 (每路口 2–8 个有效), 每 5 s 决策, 黄灯 2 s | 本项目决策更密 (5 s 对 10 s), 最短绿由 F1 掩码保证 (5 s); RESCO 的 10 s 动作时长等价于 7 s 最短绿 |
| 最短绿 | 隐含在 10 s 动作时长里 (7 s 绿 + 3 s 黄) | F1 决策时掩码, 5 s | 等价做法 |
| 最长绿 / 最长红 | **未提及, 无约束** (相位可被连续选择, 与本项目原状相同) | max_green 只是名义值 | 本文 §6.1 最长等待掩码; 这是本项目超出 RESCO 的地方, 但 Kwesiga 2024 / Müller 2022 / CVLight 已有同类 |
| 黄灯 | 由环境强加, 不在动作空间 | 同 (set_next_phase 自动插黄灯) | 相同 |
| 奖励 | 可选: 系统行程时间、近似信号延误 (当前速度与限速之差)、总等待、平均排队、压力; 各算法按原文定义 (IDQN 用 −总等待, MPLight 用压力) | −Σ 优先级权重 × 各类平均本次访问等待 / 100 (visit 口径) | RESCO 无车型权重; RESCO 的等待来自 SUMO 累计等待 (含上游继承), 正是本项目 10-26 修掉的口径 |
| 车型 / 优先级 | 无 (全部车辆同质) | 小汽车 / 公交 / 救护车, 权重 1 / 4 / 5 等 | 本项目的研究对象, RESCO 不覆盖 |
| 评估协议 | 5 个随机种子; 学习曲线 5 集滑窗; 表格报 **最好的一集** (非最终集) 跨种子平均; 指标: 延误、行程时间、等待、排队 | best 检查点 (3 次评估滑窗选) × 10 个未见种子, 逐秒口径; 报停车时间/次数、延误, 分车型; 换车型孪生 (新) | 都报 best 而非末集; 本项目种子更多且评估种子与训练种子分离; RESCO 明确指出 MPLight 训练后期发散 (区域任务 > 200 s 延误), 与本项目用 best + 末段稳定性核对的动机一致 |
| 锁死 / 发散的处理 | 未处理 (只报告发散现象) | 锁死审计 + 最长等待掩码方案 | 超出 RESCO |
| 基线 | 定时、最大压力、Greedy (最大联合排队 + 接近车数) | 定时周期、GS (排队打分)、旧口径各臂 | 类似; 本项目缺 "规则抢占" 基线 → 本文 §6.2 补 |
| 算法 | IDQN、IPPO、MPLight、MPLight*、FMA2C; 结论: 独立 DQN 在真实路网多数任务最好 | 单个共享 DQN (double, huber, 目标截断) 控制 18 路口 | 一致之处: 简单 DQN 在真实路网上够用 |
| 结论性发现 | "先前算法对感知假设和非理想路口布局不鲁棒" | 本项目的发现: 口径、检测范围、车型稀疏对优先级结论的影响 | 方向一致, 本项目更细 |

结论: 最长绿 (本文改为最长等待)、上游/通信区检测、放大稀疏到达量、侧路惩罚, 文献里都有先例, 本项目原来都没做, 这次补上是跟上常规; 优先级加权汇总与同车换型的配对评估是本文自己的做法, 论文里要单独论证。
