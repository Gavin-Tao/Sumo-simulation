╔══════════════════════════════════════════════════════════════════════════════╗
║  0. 一句话结论                                                               ║
╚══════════════════════════════════════════════════════════════════════════════╝

  西侧红色 = 一条真实的结构性瓶颈走廊 (Aungier St → Redmonds Hill 合流 →
  Peter's Row 出口) + 两处次级真瓶颈 (Cuffe St / George's St 路口), 叠加
  三种可视化伪影 (amb 每边仅 15 次通过、10m 级短边画成"红点"、fixed 面板
  的"空街红灯"效应)。它不是 bus 线路集中造成的, 也不完全是小样本噪声 —
  bus 在震中边有 ~495 次通过, 40s 等待是统计可靠的真值。

  为什么其他路口全绿: amb 只触及 212 条边中的 41 条, 其中 23 条等待恰为 0;
  bus 触及 93 条, 60 条为 0、88 条 <5s。红色需要四个条件同时成立 —
  单车道断面 + 高小汽车负载 + 下游是非 RL 控制的 priority 合流 + 边界出口
  漏斗 — 全网只有西南角这一处四条件齐备。

  拓扑 (从 net 连接图实测):

     -532427444#2 Aungier St 南行, 1 车道, 240 car + 33 bus + 1 amb /ep ─┐
                                                                          ├→ 合流
      341583777#0 Redmonds Hill,        576 car/ep ──────────────────────┘
                          ↓
      路口 cluster_2384200130_2384200132_389663, type=priority (非 RL)
                          ↓
      369977731 Peter's Row, 788 car/ep, 是 16 个边界出口之一

  即: 全网西南象限的流量 (788 辆/h ≈ 全部 car 的 17%) 经一个"让行合流"挤进
  一个出口边。Aungier 侧是支路让行方向, 高峰下等不到 gap → 队列沿 1 车道的
  -532427444#2 回溢。这解释了:
    • 为什么 bus 40s / amb 110s 都发生在同一条边 (同一个物理队列);
    • 为什么 RL 治不了它 — 该合流点不在 18 个 RL 信号里, 也不在当初 27 TLS
      集合里 (demoted_tls.json 的 9 个降级名单里没有它, 它在 OSM 里本来就
      不是信号灯), RL 的动作空间根本触不到这个瓶颈;
    • 为什么 fixed 同样差 (bus 36.7s vs RL 40.0s, 同量级) — 病根在信号
      控制范围之外, 两种控制器都只能把队列"搬家"(见 §4)。

  次级真瓶颈 (同为西南):
    • 38192817 Cuffe St (337 car/ep, 2 车道) → gneJ46 priority: 同样是
      非 RL 让行节点, bus 11.8s / amb 8.4s, fixed 与 RL 打平 → 结构性。
      (这就是 EDGE_FIGURES_METHODS 里如实保留的 car +50% 回归边。)
    • 317003249#2 George's St (135 car/ep, 21.6m 短边) → TLS 1448436:
      这是 RL 控制内唯一 prio 比 fixed 更差的西侧点 (speed 3.7 vs 4.3),
      属于可归因于策略的真回归, 值得单独看该 TLS 的相位行为。

    (4.3m)、317003249#2 (21.6m) 都是 10~20m 级短边, 队尾扫过即整边变红,

    这些短边的值本身不假, 但视觉权重被严重放大 — 一个 10m 红点与一条

  伪影 C — fixed 面板的"空街红灯": 532427444#0 (Aungier 北行) 上 car/bus

    95.3s (speed 1.0 m/s) → fixed 面板深红。这不是拥堵, 是固定配时对
    零需求进口不给绿。RL 把它降到 2.5s — 顺带是"RL 优先机制生效"的一个

╔══════════════════════════════════════════════════════════════════════════════╗
║  4. "队列搬家": fixed 与 RL 的红色为什么不在同一段                           ║
╚══════════════════════════════════════════════════════════════════════════════╝

  amb_0 的路径纵贯整条西侧走廊 (Dame St → George's St → Aungier → Peter's
  Row 出口)。沿线逐边对比 (amb speed, m/s):

    edge              街道           fixed    prio(RL)
    -5826896#0        George's St     0.9  →   7.1     RL 治好
    -554991019        Aungier 上段    1.9  →   6.4     RL 治好
    -532427444#2      Aungier 末段    5.2  →   1.0     RL 更差
    (bus 等待同构: -554991019 78.7→3.2s, -532427444#2 36.7→40.0s)

  解读: fixed 把队列压在走廊上游 (George's St 一带的红灯), RL 提高了上游
  信号放行效率, 于是同一股流量更快地灌进末端 — 而末端合流点不受任何信号
  控制, 队列整体向下游搬家, 停在 RL 权力边界外的最后一段。走廊总延误
  两者同量级, 只是红色的位置不同。这是"局部信号优化 vs 网络瓶颈守恒"的
  典型现象, 可以直接写进论文 limitation, 也是 §6 方案 S2 的动机。

  ── 5.1 是数据抽取/注入方式造成的吗? ── 部分是, 但不是主因 ──────────────────

  • amb 注入 (曝光模型): 4 条路线里 3 条集中在西/西北 (入口按消防站距离、
    出口朝医院方向加权), 所以 amb 的红色"只可能"出现在西侧 — 注入设计决定
    了 amb 在哪里被观测, 但不制造拥堵本身。
  • car 标定: NNLS 解出的流量把 576 car/ep 放在 Redmonds Hill、337 放在
    Cuffe St, 这两股是否被高估值得复核 (对照 calibration_report_11h.json
    的该行残差); 若被高估, 西南红会同比例夸大。
  • 边界裁剪: Peter's Row 是裁剪产生的出口边。出口本身不限流 (车辆到达即
    消失), 瓶颈在其上游的让行合流 — 该合流在真实路网中同样存在, 但真实
    Dublin 的 Kevin St/Redmonds Hill 一带是有信号协调的; 模型里它退化成
    无信号 priority 节点, 这是"网络抽取"引入的真实失真 (见 S2)。
  • departLane/insertion: 排除。逐边红色与入口边无关, 且管线实测
    DepartDelay≈0.5s、无插入积压。

  ── 5.2 与车道位置有关吗? ── 有一点, 通过"锁道"间接起作用 ────────────────────

  全部车辆 lc*=0 锁道 + amb 无 bluelight/speedFactor: amb 在 1 车道的
  Aungier 末段排在 240 car/ep 的队伍里, 与普通车完全同待遇, 现实中救护车
  会借对向/穿插。所以 amb 的绝对等待是悲观上界 (设计使然 — 优先必须由
  信号侧学出来)。但"红在西南"这个空间格局与锁道无关, bus/car 同样红。

  ── 5.3 此前口头分析的修正 (数据推翻的部分, 记录在案) ────────────────────────

  ✗ 旧说法 "bus 红 = 线路集中走廊 + 锁道的拓扑必然":
    错。bus 班次最集中的是 Nassau/Grafton 走廊 (50~64 班/ep), 等待 0~1.1s
    全绿; 红色的 Aungier 只有 33 班/ep。集中度与红色无相关, 决定因素是
    断面车道数 + car 负载 + 下游控制类型。
  ✗ 旧说法 "amb 红主要是小样本噪声, 不是系统性拥堵":
    半错。样本确实小 (15 次/边) 且数值不可靠, 但红色位置与 bus 大样本
    完全重合 → 走廊拥堵是系统性的、真实的。
  ✗ 旧说法 "震中是 St Stephen's Green 西侧 + Grafton 街区":
    定位不准。Grafton 全绿; 震中是 Green 以西一个街区的 Aungier St/
    Redmonds Hill→Peter's Row 合流 + Cuffe St, 属"西/西南"无误但街区搞错。
  ✓ 站得住的: amb 单边数值不能当证据引用; 注入模型决定 amb 空间分布;
    锁道+无 bluelight 使 amb 等待为悲观上界; 边界插入可排除。

      替代手工 DROP_AMB 名单 — 原则化、可写进论文、审稿人无法指摘。
   b. 色标改 per-class 分级或对数化: 现在三类共用 [0, 28.2s], bus 40s 与
      amb 110s 都饱和成同一种红, 图丢失了量级信息。
   c. amb 汇报口径从"单边"改"走廊": 按 amb 路线聚合成 O→D 全程行程时间
      (15 seed 配对 fixed vs RL), 样本单位从边升到行程, 统计上站得住。
   d. 边级图加通过量线宽编码 (lw ∝ log 流量), 10m 红点的视觉权重自然回落。

  ── S2. 结构修复: 把真瓶颈纳入控制或如实声明 ────────────────────────────────
   a. 核实 cluster_2384200130 (Aungier/Redmonds Hill 合流) 与 gneJ46
      (Cuffe St) 在真实路网中是否受信号控制 (SCATS 站点表/实地影像)。若是,
      当前 priority 建模是失真 → 把它们补进受控集合 (作为 fixed 配时或
      第 19/20 个 RL agent) 是最正当的修复; RL 拿到瓶颈的控制权后, §4 的
      "队列搬家"问题才有解。
   b. 若确认现实中就是无信号让行: 保持现状, 在论文里把 §4 写成 limitation
      ("信号优化无法消除控制范围外的合流瓶颈, 只能改变队列位置"), 这本身
      是个诚实且有内容的发现。
   c. 复核 NNLS 对 Redmonds Hill (576/ep) 与 Cuffe St (337/ep) 两行的
      拟合残差与 SCATS 目标, 排除西南流量被解到上限的标定伪影 (历史上
      Duke St 出过同类问题)。

  ── S3. amb 评估功效 (治"15 次通过"的根) ────────────────────────────────────
   a. 评估期让 amb OD 逐 seed 重采样 (训练场景不动, 只在 eval 生成器里换
      seed): 15 个 seed × 不同路线 → 空间覆盖与有效样本成倍增长, 单边
      n 也随之上升; 这与既有结论"amb 评估 underpowered, 永不引用单次
      eval 的 amb 数字"一致, 是它的根治版。
   b. 或者最小改动: eval seed 从 15 → 50 (只影响收集脚本运行时长)。
   c. 论文措辞: amb 空间分布由曝光模型合成 (DFB 无事故坐标), 单边 amb
      热图仅作定性展示, 定量结论一律用走廊级/全网级配对统计。

  ── S4. [已被 §7 修订] 317003249#2 不是策略回归 ─────────────────────────────
   初版曾把该边列为"唯一 RL 可归因回归"(speed 4.3→3.7)。§7 的等待数据推翻
   此判断: 该边是 TLS 1448436 的进口道 (reward 可见), RL 把 bus 等待
   10.4→2.2s、amb 10.2→1.9s, 均大幅改善; speed 微降是 21.6m 短边上
   时间加权均速对"缓行不停车"状态的度量伪影, 不是策略问题。无需行动。

╔══════════════════════════════════════════════════════════════════════════════╗
║  7. RL 实现为什么留下红色: reward 盲区机制 (2026-07-02 补章, 核心发现)        ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 7.1 实现事实 (代码定位) ──────────────────────────────────────────────────

  reward: make_priority_avg_waiting_reward (rewards.py:896) 的热循环是
    `for lane in ts.lanes` (rewards.py:930), 而 ts.lanes 只含
    getControlledLanes(自身进口道) (traffic_signal.py:104)。
  → 车辆的等待只在它位于"某个 RL TLS 的进口道"上时被读取。但注意
    (2026-07-02 修正, 由"出口道=下家进口道"的追问触发): 读的是
    getAccumulatedWaitingTime (memory=1000s, env.py:102), 且跨车道扣减
    (rewards.py:937-940) 只扣"在其他计费车道上已记录"的部分 —— 所以
    盲区边上攒的等待并非恒为 0, 而是分两类:
    • 中段盲区 (下游还会经过 RL TLS, 如 -532427444#6/#7, Cuffe St 的
      amb 方向): 等待被"延迟记账"— 车驶入下一个计费进口道起, 盲区旧账
      全额记入该 agent (env.vehicles 首见记 acc 全额), 且 reward 是
      水平量 (非差分) → 车停留在该进口道期间每一步都持续计入, 直到
      驶入再下一条计费车道才做增量扣减。有账单, 但该 agent 的信号动作
      影响不了上游 priority 路口的排队 → 有账无杆。
      注意区分: "逐边清零"只存在于可视化采集口径 (edge_waiting_collect
      的 inc=acc−dprev, 每边只记本边新增); reward 侧 episode 内无清零,
      env.vehicles 仅在 reset 时清空 (env.py:207,320)。
    • 末端盲区 (下游直到出网出口都不再经过任何 RL TLS): 等待永远不被

  ── S5. 面向 reward 盲区的方案 (不动代码, 供决策) ───────────────────────────
   a. 出口道计费: reward 加下游项 (agent 出口道排队×β)。exp208 的 obs
      已有 outcq, 状态侧现成; 只覆盖"TLS 出口道"型盲区 (-532427444#2 是
      389281 的出口道, 可覆盖), 覆盖不了走廊中段的 #6/#7、gneE51/52。
   b. 行程级/走廊级 reward: 车辆的等待始终计给其路线上"下一个 RL TLS"
      (route-aware attribution) → 所有盲区边自动归属到某个 agent, 无边
      漏计; 实现成本高于 a, 但语义完整, 且与 amb 走廊行程时间的论文
      口径一致。
   c. 全局项混合: r = (1-α)·local + α·global_waiting。最便宜但信用分配
      被稀释, CoLight 系已知会放大方差, 与 R-campaign 的稳定性结论有
      潜在冲突, 列为下策。
   d. 与 S2 正交: 把合流点升级为受控信号后, #2 变成新 agent 的进口道,
      自动脱离盲区 —— S2 与 S5 任一都能覆盖震中, 同时做则互为保险。
   决策提示: a 是最小改动且直击震中; b 是论文叙事最优 ("reward 作用域
   = 控制作用域"的错配是 decentralised TSC 的一般性问题, 修法本身可作
   贡献点); c 不建议。
