╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 0: TL;DR — 选型判决                                                   ║
╚══════════════════════════════════════════════════════════════════════════════╝

  问: T 做多路口协同, 用 GAT / Coeff / concat / 还是别的?
  答: **边界 token (T 原生) 主推; GAT-on-CLS 做对照臂; Coeff 不给 T 配;
      concat 不适配。**

  方案            对 T 适配      关键理由 (含实测)
  ───────────     ──────────     ──────────────────────────────────────────
  concat state    ✗ 不适配       T 的 obs 是 token 矩阵不是平向量; concat 破坏
                                 集合语义 + 维度×5 + 带回位置包袱。concat 本质
                                 是"权重固定=1 的 attention", T 已付 attention
                                 算力, 再 concat = 拒收它的收益
  Coeff (β奖励层) ✗ 不配         失败与 state 无关: 邻居 reward 与本地动作有
                                 5-50s 因果延迟, β→0 是降 target 方差的稳定
                                 吸引子。两次实测死亡: 可学 β→0 (exp145/147
                                 精确为零), GAT-β 熵卡 ln2 (链上邻居 reward
                                 高相关, 无判别梯度)。T 蹭 exp187(B) 结论即可
  GAT-on-CLS      △ 对照臂       spec 预留挂接点 (h_int=CLS 输出), 机制成熟;
                                 但 (a) 邻居信息压进 128 维 CLS = 瓶颈丢细节,
                                 "邻居链路有救护车"被 squash 成一个向量;
                                 (b) CoLight 是实测的倒挂放大器
  边界 token      ✓ 主推         多路口下 t 出口链路 == e 进口车道, 那条车道在
  (本文)                         e 那里本就是一个带 φ 的 token; 并进 t 的 token
                                 集, 同一 encoder 自动学"看不看邻居/看哪条道"

  为什么边界 token 是结构正解 (一句话):
    T 的全部赌注 = "attention 自己学该聚合什么"。协同对它只是扩大感受野,
    不需要新机制 —— 比 concat 好 (可学权重的 concat 超集), 比 GAT-on-CLS 好
    (无 128 维瓶颈, 优先级以桶粒度跨路口传递), 与 Dublin 网络级路线同构。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 1: 设计 — 边界 token 是什么                                           ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 1.1 物理基础: 同一条车道, 两个路口的两个角色 ───────────────────────────
    1x3 链 t — e — J0 里, t 的东出口车道 == e 的西进口车道 (同一段物理车道)。
    对 e: 它是进口, 本就是 e 的 token 集里一个带 φ 的 token。
    对 t: 它是"我的下游", 我灌进去的车去那里。把它作为 t 的一个 REMOTE
          token 并入, t 就"看见"了下游链路的占用与优先级构成 —— 包括驶来的
          救护车 (以 p5 桶非零的 token 形式)。

  ── 1.2 remote 车道的定义 (generic, 与边名无关) ───────────────────────────
    remote(t) = { 本路口出口车道 } ∩ { 任意其它信号路口的受控进口车道 }
    实现从 getControlledLanes / getControlledLinks 一次性推导 (出口 = 各
    controlled link 的 to-lane; 邻居进口 = 其它 TLS 的 getControlledLanes)。
    不读 net.xml、不需要 neighbor_map、不假设拓扑 —— 三岔/Dublin 同样成立。

  ── 1.3 token 结构 ──────────────────────────────────────────────────────────
    token = [is_remote(1)] + [service(K)] + φ(fields)
      own token   : is_remote=0, service=本路口放行该道的相位 multi-hot
      remote token: is_remote=1, service=0 (邻居的相位放行它, 在本 agent 的
                    动作空间里无意义 → 置零; is_remote 位即 role 标志);
                    perphase 模式的 is_green 同理置 0
      padding     : 全零 token, 补到全网统一的 remote 槽位数

  ── 1.4 同构性: 为什么共享 agent 仍成立 (G4) ──────────────────────────────
    remote 槽位数 = 全网各路口 remote 车道数的 MAX (1x3: e 有左右两邻居 ×3 道
    = 6; t/J0 端点各 3, 补零到 6)。所有路口 token 数相同 → obs 维度全网一致
    → 单共享 agent / 单共享 Transformer 照常 (与 G4 的 padding-to-max 同思路,
    这里 padding 的是 remote 段)。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 2: 与 ψ / GAT-on-CLS 的关系                                           ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 2.1 边界 token = ψ 的富化版 ────────────────────────────────────────────
    ψ (ABT_OUTGOING 主方案): 每单元 +2 标量 [出口占用, 出口排队] — type-agnostic。
    边界 token: 把那条出口链路的完整 φ (5 桶 × 字段) 作为 token 给进去。
    差别正是"容量侧 type-agnostic"原则 (I6) 的一个有意破例:
      - ψ 回答"下游堵不堵" (协同里只要这个就够时, ψ 更省);
      - 边界 token 还回答"下游堵的是谁" —— 对 amb 问题是实质差异:
        下游链路上的救护车以 p5 token 可见, 而 ψ 的 type-agnostic 标量
        会把它混进总占用。
    递进关系: ψ (L0.5, 最省) → 边界 token (优先级桶粒度的协同)。E1b 的
    gain_ratio 框架对两者通用。

  ── 2.2 边界 token vs GAT-on-CLS — 为什么前者对 amb 更好 [推测] ─────────────
    GAT-on-CLS: 邻居的整张 state 经 GAT 压成对 h_int(128) 的一个贡献向量。
      下游链路上稀疏的救护车信号, 和邻居全路口状态挤进同一个 128 维瓶颈 ——
      这正是 1x3 倒挂因果链里"稀疏类信号被高频类淹没"的重演, 只是搬到了
      协同通道。
    边界 token: 救护车作为一个独立 p5 token 进入 attention, CLS 可以直接对它
      赋高权重 (attn_on_amb 可观测)。优先级信息以桶粒度跨路口, 不经瓶颈。
    → 预测: 在 amb 指标上 边界 token ≥ GAT-on-CLS; 在 system 效率上两者
      接近 (都引入了下游信息)。exp188 vs (将来的 T+GAT 对照臂) 可验。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 3: 实现与验证 (已落地)                                                ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 3.1 代码 ────────────────────────────────────────────────────────────────
    PriorityLaneTokenNbObservationFunction (observations.py) — 继承 T 类,
      复用全部 φ/service/memoize 机制; __init__ 推导 remote 车道 + 统一槽位,
      __call__ 发 own token → remote token → padding。token_layout 加 phi_off
      契约 (新类 token 多 is_remote 位, train.py 的 attn_on_amb 诊断改读 phi_off,
      旧类向后兼容)。
    接线: train.py / eval_unified registry + obs_remote_slots 透传。
      **无需 neighbor_map, 无需特殊 trainer** — obs 层协同, 跑 plain train.py。

  ── 3.2 验证 (1x3 NS20bus, 实测 ✓) ─────────────────────────────────────────
    · remote 身份正确: t→{t_e_*} (正是 e 的西进口), e→双侧 6 条, J0→{-E0_*}
    · 槽位统一: =6 (取自 e), t/J0 各补 3 个零 token
    · 维度跨 ts 一致: 三路口全 365 (18 token×20 + header 5) → 共享 agent 成立
    · remote token 的 φ == TraCI 真值 (逐桶核对)
    · is_remote: own=0 / remote=1 / pad 全零
    · e2e: transformer 18×20 + phi_off=5 流到 attn 诊断, exit=0

  ── 3.3 实验定位 ────────────────────────────────────────────────────────────
    exp188 (T + 边界 token) 与 exp185 (T 无协同) 单变量差 = obs 类。
    1x3 协同阶梯五臂:
      184 B-cqm 无协同 (L0)        | 185 T-cqm 无协同 (L0, T baseline)
      186 B-cqm CoLightOrig (L1)   | 187 B-cqm CoeffDQN-β (L2)
      188 T-cqm 边界 token (T 原生协同)  ← vs 185
    跑批: run_abt_1x3.sh (顺序, 各臂自动映射到对应 trainer)。

  ── 3.4 不变的提醒 (协同选型 ≠ 排序保证) ───────────────────────────────────
    三重实测: 协同放大倒挂 (容量/CoLight/CoeffDQN 三证)。T 在 1x1 已有倒挂
    倾向 (ns) + attn_on_amb=0.05 (没在看救护车)。
    → 188 (及任何 T 协同) 在 1x3 解读时, "协同增益"与"倒挂加深"分开记账;
      协同选型管效率, 排序还是 PRIORITY_ORDERING 的 G1/Y1 的活;
      1x3 批应配 stratified replay (对 attn_on_amb=0.05 的病根)。
