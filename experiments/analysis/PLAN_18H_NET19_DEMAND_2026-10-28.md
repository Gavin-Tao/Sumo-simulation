# 18 点场景车流生成 实现计划 第三版 (2026-10-28, 供外部审阅)

> **执行方式:** 按任务顺序执行, 每个任务有可检查的交付物与核对命令, 步骤用复选框追踪。全部只产出场景文件与核对工具, **不启动任何训练**。两轮外部审阅意见的逐条处理记录见 §10 与 §11。

**目标:** 在 corridor 路网上生成 18 点场景的小汽车、公交、救护车车流, 满足五点:
1. 以真实数据为中心浮动: 小汽车按 SCATS, 公交按 GTFS, 救护车数量按都柏林消防队救护车出车数据。
2. 好训练: 每集由轻到重, 没有长期顶满的车道。
3. 能体现优先级规格: 优先车辆经过有取舍的转向。
4. 不出现真正的堵死, 也不出现 "刚放空又排满"。
5. 起点、终点与注入方式不污染 RL 学习、不引入偏差。

**范围:** 只做 18 点场景。50 辆公交 + 50 辆救护车的同路线新场景是下一个任务。

**做法概述:**
1. 列出可用的车辆入口与出口白名单。
2. 在车道图上精确搜索每个受控转向的候选路线: 全程不换道、不重复经过 RL 路口、终点在边界出口。
3. 小汽车用线性规划把路线车数拟合到逐转向需求; 公交沿用 GTFS 线路; 救护车走一条设计路线。
4. 把同一入口车道上所有车型的车合在一起排出发时刻。
5. 用三种与学习无关的控制器标定: 固定轮转、保证服务的排队驱动轮转、随机 (只作压力测试)。

**技术栈:** SUMO + sumolib + networkx + scipy (linprog/highs)。复用以下现成部件:
- `nets/dublin/build_corridor15/routing.py` 的车道图路由器;
- `generate_scenarios.py` 的线性规划拟合;
- `experiments/tools/dublin/scenario/scenario_check.py` (第二版, 本计划扩展为第三版)。

**依据 (审阅时请一并阅读):**
- `experiments/analysis/NET19_JUNCTION_AUDIT_2026-10-28.md`: 19 信号网逐路口审计。
- `experiments/analysis/SCENARIO_PRIORITY_PAIRS50_DESIGN_2026-10-27.md` §4: 有效决策机会定义。
- `experiments/analysis/DESIGN_UPSTREAM_AND_PRIORITY_AGG_2026-10-27.md` §7: 同参数车型与换车型孪生评估。
- `nets/dublin/build_corridor15/net19/README.md`: 路网构建记录。

## 2. 起点与终点

### 2.1 已知偏差来源与对策

| 偏差来源 | 机制 | 对策 |
|---|---|---|
| 在 RL 进口道上发车 | 车凭空出现在排队中间, 观测跳变; 插不进去的车在网外等, 指标看不见。旧 18h 改道版 37% 的车如此, 每集积压 250–320 辆 | 禁止; 只在白名单入口发车 |
| 插车受策略影响 | 某策略让排队顶到入口时插车推迟, 网外等待不计入, 该策略显得 "更好" | 入口离第一个 RL 停车线有距离; 按入口统一排时刻表; 标定与评估都按入口、车型报请求数、实际插入数、未插入数、出发延迟、未完成车辆 (§6) |
| 中段插车与穿行车流抢空档 | 插车时机取决于上游 RL 路口放出的间隙 | 支路入口只选上游来车很少的车道 (§2.2)。这只是筛选条件, 不等于证明无偏差, 仍以 §6 的按入口报告为准 |
| 路线结束在 RL 进口边 | 车在边末消失前排在队尾, 人为回溢; 访问没有出口 | 只在边界出口离网 |
| 起终点附近的非 RL 让行口 | 让行等待不进 RL 指标; 回溢会堵住 RL 路口 | 让行口主路预算 (§2.4) + 逐节点非 RL 停车报告 + 出口回溢直接测量 |
| 路线重访 | 统计器把两次经过并成一次访问; 形成策略自激回路 | 生成时禁止 |
| 空网起步 | 前几分钟网内无排队 | 每集时间曲线 (§3.4); 救护车只在平台期出发 |

### 2.2 入口白名单

1. **边界入口:** 无来边的边。NET18B 有 15 条 (北臂人工入口已删), 边界出口 15 条。其中经过非 RL 让行口才到第一个 RL 路口的, 只能在让行预算内使用。
2. **支路入口:** 非 RL 道路上的车道, 必须同时满足:
   - 车道长 ≥ 40 m;
   - 所在边两端都不是 RL 路口;
   - 设计车流中, 该车道的上游来车 ≤ 该车道发车量的 10%;
   - 到第一个 RL 进口之间不经过让行连接;
   - 离第一个 RL 停车线 ≥ 60 m。
3. 19 信号网上的初步搜索找到的支路入口: `2294384#0_1` (151 m)、`419502786#0_2` (191 m)、`7849019#2_1` (68 m)。`419502786#0_2` 的上游接 cluster_1998326407 南右转出口, 必须带设计流量核对第 2 条中的上游来车条件。最终清单以任务 2 在 NET18B 上的结果为准。
4. 生成器写文件前断言每辆车的出发车道在白名单内。

### 2.3 按入口车道统一排时刻表

- **转向分配:** 用 `turn_ratios_18h.json` 的方法在 NET18B 上重算先验, 并参照旧 18h 小汽车路由的过境量。
- **不设逐转向硬下限。** 要求放在路口层面: 每个 RL 路口至少有一对互斥运动在平台期都有需求, 且优先车辆能遇到放行取舍 (C11)。只有某路口因先验几乎为零而无任何可学取舍时, 才对其支路运动小幅补量; 每个路口补量合计 ≤ 总量 10%, 逐条记录为 "偏离真实"。
- **按车道共同占用与绿灯服务能力定需求:** 共享车道、短进口、多相位路口, 以 "同一车道上各运动需求之和 ÷ 该车道可获得的绿灯服务能力" 估算, 起始估算值 ≤ 0.6 的车道才算有余量。这只是起始检查, 是否下浮由 §5 判据决定。

### 3.2 公交 (GTFS 18 点)

- 18 点共 262 辆, 用 corridor 已修复终点的路线投影到 NET18B。
- 每条路线两端用路由器延伸到白名单入口与边界出口; 重访 RL 路口的 8 辆截断到第一次经过之后的出口。
- 每条 GTFS 线路班次 × 0.8–1.2, 起始 1.0; 出发时刻保留 GTFS 时刻, 加 ±60 s 抖动。
- 若某路口没有公交经过其竞争运动, 先在 1.2 倍内加密经过该处的真实线路; 仍没有时才补非 GTFS 车次, 合计 ≤ 公交总数 10%, README 单独标注。
- 公交路线集中在主干, 与救护车的总体分布不对称。评估不要求公交与救护车的类平均结果镜像对称 (§6)。

### 3.3 救护车 (数量符合真实, 一条设计路线)

**数据说明:** `dublin_sumo_files/2023-open-data-dfb-ambulance.csv` 是都柏林消防队 (Dublin Fire Brigade) 的**救护车**出车记录, 不是消防车。都柏林市区的急救救护车由消防队运营、从消防站出车, 所以记录按消防站归属。时间字段包括到达现场、离开现场、到达医院。全国救护车服务 (HSE National Ambulance Service) 在都柏林也有车辆, 但不在这份数据里, 所以下面的数是偏保守的下限参考。

**数量依据:** 260 个工作日, 18 点 (接警时刻) 的出车数:

| 消防站 | 每工作日均值 | 中位 | 90 分位 |
|---|---|---|---|
| Tara Street (紧邻本区域) | 1.43 | 1 | 3 |
| Dolphin's Barn | 1.35 | 1 | 3 |
| Donnybrook | 0.38 | 0 | 1 |
| 三站合计 | 3.15 | 3 (10 分位 1) | 5 |

这些是消防站的出车次数, 不能直接推出每小时经过这片路网的救护车数。本场景是**参考出车数据设定的低频场景**: 每集固定 3 辆, 这是设计选择。理由:
- 训练样本是 1 辆的三倍。以往每集 1 辆时优先级 5 的特征没被拟合, 根本原因是样本太少。
- 量级参考: 三站 18 点合计出车的中位数是 3。
- 3 辆对上千辆背景车几乎没有扰动; 同路线间隔 ≥ 300 s, 彼此不粘连。
- 数量固定, 不同优先级规格、不同训练集之间的救护车指标口径一致。

**一条路线 (用户 2026-10-28):** 所有救护车都走同一条设计路线, 时刻表之间只变出发时刻。选线要求 (让少量车辆提供尽量多的有效样本):
- 经过的 RL 路口尽量多, 至少 6 个。其中 ≥ 5 次是非恒绿的竞争运动, 两类都要有:
  - 两相位主支路口的支路运动, 考验 "肯不肯打断主流";
  - 多相位均衡路口 (如 1448442、389281、cluster_21620852), 考验 "换哪个相位"。
- 起点用边界入口, 离第一个 RL 停车线 ≥ 100 m; 终点为边界出口。
- 不重访; 经过的让行连接都在 §2.4 预算表里, 优先选不经过任何让行连接的。
- 任务 6 在候选中按 "竞争运动次数 × 平台期有排队概率" 打分选出; 前 3 名在 README 里列出备选与理由。

**出发时刻:**
- 在高峰平台期 900–2700 s 内分三段各抽一辆 (900–1500、1500–2100、2100–2700 s), 相邻两辆间隔 ≥ 300 s。
- 与同路线的 GTFS 公交不在同一分钟出发, 避免粘连。

**防记忆:**
- **时刻表分工 (共 7 份, 出发时刻各不相同):** 第 1–5 份训练轮换 (轮换需 D6; 未批准前训练只用第 1 份, README 注明); 第 6 份用于标定与调参 (C11 用它和第 1–5 份), 不参与训练; **第 7 份是最终测试, 定稿前不跑、不据其结果调任何需求。** 公交的 ±60 s 抖动按同样 7 份分工。
- 只有一条路线, 模型可能记住 "救护车总从这几个进口来"。评估用的未见路线 (§6) 专门检验这一点。
- 救护车 id 固定 `amb_01`–`amb_03`, 以便换车型孪生评估。

**风险:** 以往每集 1 辆时, 优先级 5 的特征没被拟合 (PRIORITY_EVIDENCE)。本场景只能靠选线、跨集轮换与增加评估集数缓解。若训练后评估没测出救护车优先的收益, 结论只能写 "本配置 (每集 3 辆) 下未证明收益", 不推广为 "真实频率下学不到"; 严格检验放在下一个任务的 50 + 50 场景。

### 3.4 每集内的时间曲线 (给学习留出余地)

| 时段 | 背景小汽车发车率 (平台期 = 100%) | 作用 |
|---|---|---|
| 0–300 s | 40% | 每集开头不是压力工况 |
| 300–900 s | 40% → 100% 线性上升 | 每集都经历由轻到重 |
| 900–3000 s | 100% | 高峰平台期; §3.1 的目标指这一段的小时发车率 |
| 3000–3600 s | 70% | 收尾, 减少集末未完成的访问 |

- GTFS 公交保留真实时刻, 不套曲线; 救护车按 §3.3 的时刻表, 也不套曲线。
- 这条曲线让每集的车流开头偏离真实的 18 点形态 (真实 18 点是整小时高峰), README 注明。

**流率与车数的换算 (统一以平台期流率为准):**
- §3.1 与 §2.4 的所有目标、上限、预算都是**平台期流率** (辆/h)。
- 线性规划的变量是每条小汽车路线的平台期流率 r (辆/h), 不是整集车数。
- 曲线积分为 0.85 小时 (0.4×300 + 0.7×600 + 1.0×2100 + 0.7×600 = 3060 s), 所以整集车数 n = round(0.85 × r)。按曲线分配出发时刻后, 平台期 (900–3000 s) 内的实际发车率等于 r。
- 公交与救护车不套曲线, 它们对平台期流率的贡献按时刻表实测: 900–3000 s 内的出发车数 × 3600 / 2100。线性规划先扣除这部分再拟合小汽车。
- 例: 某路线平台目标 1000 辆/h, 整集应发 850 辆。若误把 1000 当整集车数再套曲线, 平台流率会变成约 1176 辆/h。

## 4. 标定控制器 (与学习无关)

| 控制器 | 定义 | 用途 |

## 5. 标定判据 (1.0 档全部通过才算定稿)

**服务周期:** 某个槽在某控制器下, 相邻两次获得绿灯的时间间隔。"服务机会" 指该控制器本应放行这个槽的那次相位。

**硬判据** (1.0 档必须通过; 主要看旧队列能否清掉、排队是否持续增长、是否回溢、下游是否阻塞):

| 编号 | 判据 | 阈值 |
|---|---|---|
| C1 全网不积压 | 在网车辆数按 10 分钟分窗, 平台期最后一窗相对第一窗的增长 | 固定轮转、排队驱动 ≤ 10%; 随机只报告 |
| C2 插车 | 按入口、车型报请求数、实际插入数、未插入数、平均与 99 分位出发延迟 | 排队驱动下: 未插入 ≤ 需求 1%; 平均出发延迟 ≤ 2 s; 99 分位 ≤ 15 s。三个控制器之间平均出发延迟差 ≤ 1 s (只是指标之一, 不单独作为无偏差的证明) |
| C3 无真正堵死 | 某进口有排队、该进口所在相位累计绿灯 ≥ 30 s, 但停车线 120 s 内无车通过; 或下游出口排满、上游无法恢复 (持续 ≥ 300 s 不回落) | 固定轮转、排队驱动 0; 随机报告并与参照比较 |
| C4 漏放与旧队列未清 | 漏放: 有排队的槽连续 2 次服务机会都没被放行。旧队列未清: 某次绿灯开始时已在排队的车, 连续 ≥ 3 次服务后仍未全部通过 | 排队驱动下漏放 0; 旧队列未清的槽-时段 ≤ 5% |
| C6 出口与下游接收 | 出口车道排到起点持续 ≥ 60 s 的事件; 9101555 两条出口、9101554、cluster_2384200130 单独列出 | 固定轮转、排队驱动 0 |
| C7 观测不越界 (仅长进口) | 进口长 ≥ 60 m 的 RL 进口: 队尾越过进口边落到上游的时间占比 (逐秒) | 排队驱动下每个进口 ≤ 5%。短于 60 m 的进口 (1448436 南 21.6 m、26165090 北 40.2 m、cluster_21620852 西 43.3 m、cluster_1998326407 北 45.3 m) 只报告, 写为已知局限 |
| C9 车辆与仿真完整性 | 换道次数、路口碰撞 (`collision-output`)、teleport、统计器缺条目、救护车到达率 | 前四项 0; 救护车到达率 100% |
| C11 优先级机会 | 按 pairs50 设计 §4 的定义, 只用时刻表 1–6 (不用最终测试的第 7 份): 救护车在其路线上 "有机会的访问" 占比; 公交每集有机会访问数 | 救护车 ≥ 70%; 公交每集 ≥ 150 次; 红灯提前放行与绿灯保持都出现 |
| C13 开局不压人 | 0–900 s 内, 排队驱动下单次访问等待 ≥ 90 s 的车次; 在网车辆数相对平台期均值 | 前者 0; 后者 ≤ 70% |
| C14 逐进口不积压 | 排队驱动下每个 RL 进口的排队车数按 10 分钟分窗, 平台期最后一窗相对第一窗 | 增长 ≤ 20% 或 ≤ 2 辆 (取宽者), 防止全网平均掩盖个别进口持续变长 |

**诊断指标** (只报告、用于定位, 不作为下调需求的依据; 短进口上正常的红灯排队会让它们读数很高):

| 编号 | 指标 |
|---|---|
| C3' 长等待 | 单次访问等待 ≥ 150 s 的车次 (不称锁死) |
| C5 清空与再满 | 每个受控槽: 绿灯结束时的残留队列; 完全清空次数; 从完全清空到再次达到进口容量 60% 所需时间 |
| C8 非 RL 停车 | 非 RL 边停车 (车·秒) 占 RL 进口停车的比例, 逐让行节点 |
| C10 有事可学 | 每个 RL 路口有排队的决策步占比 (固定轮转); 目标 20–40%, 低于 10% 的路口列出 |
| C12 车道压力 | 平台期每条 RL 进口车道有排队的时间占比、排队超过容量 60% 的时间占比 |

**不达标时的处理:**
- 先定位原因, 分四类:
  - 需求过高 (排队驱动下也不过);
  - 让行口或下游接收不足 (C6、C8);
  - 插车问题 (C2);
  - 几何或碰撞问题 (C9)。
- 只有第一类 (由硬判据 C1、C4、C14 判定) 按路口下调 s_j (每次 0.1, 保持转向比例)。第二类收紧预算或改路线。第三类改入口或时刻表。第四类报给用户。
- 最多 4 轮, 每轮写 README。s_j 低于 0.8 或 4 轮仍不过的路口, 报给用户决定。

## 6. 评估设计 (供训练后使用, 本计划只准备文件)

- **主比较:** 固定需求、路线与时刻表, 比较同一类车在 111、531、351 下的变化, 每臂多种子。不要求 531 与 351 的类平均结果镜像对称: GTFS 公交与救护车的路线分布不同。
- **换车型孪生:** 同一份车流里, 把救护车与 GTFS 公交逐辆换成 `car` 身份 (路线、时刻、位置不变) 另跑一遍, 得到同位置、同时刻的配对差。
- **主结果用每集 3 辆的原场景, 增加独立评估集数:** 在最终测试时刻表 (第 7 份) 之外, 场景定稿后再用同一生成器、新种子生成若干份只用于评估的时刻表 (路线与辆数不变, 只变出发时刻); 每份 × 多个 SUMO 种子, 合计 ≥ 30 集 (≥ 90 次救护车行程) 每臂。
- **补充: 救护车频率变化测试 (只用于评估):** 同一份背景车流上每集约 20 辆救护车 (间隔 ≥ 100 s), 并配同路线、同时刻的小汽车孪生版本。它改变了救护车出现频率, 可能改变控制器行为, 只作补充, 不替代主结果。
- **未见路线探针:** 3 条不与训练路线共享 RL 进口的救护车路线, 检验学到的是 "救护车优先" 还是 "这几个进口优先"。
- 探针与评估时刻表文件不得被任何训练配置引用。
- **按入口报告插车:** 评估输出按入口、车型的请求数、实际插入数、未插入数、出发延迟与集末未完成车辆, 与路口指标一起报。
