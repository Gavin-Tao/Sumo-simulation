  C5 ⭕ "PriorityMovement 怎么处理多同向车道 / 共享车道?" (用户问题, 代码核查)
     —— 多对多 lane↔movement 映射, 两种情况分开看 (实测 observations.py):

     ① 多条同方向车道 (如两条 N 直行) —— 干净聚合, 无瑕疵:
        connection 同属一条 from_edge、同一 to_edge → 进同一 slot (N-T)。
        · 车辆: 两车道的 N-T 车全累加进 slot_stats[N-T] (count/queue/wait 求和);
        · 容量: cap[N-T] += lcap 逐条 feed 车道累加 → 两车道容量正确相加;
        · 归一化 density = 两车道总车 / 两车道总容量。多对一聚合 = movement
          粒度本意, 完全正确。

     ② 共享车道 (一条车道既直行又右转, 多 connection 去不同 to_edge) ——
        车辆分得准 (含 count 不重复), 容量有近似瑕疵:
        · 车辆归类 (准): _vehicle_slot = route 的 (from_edge, 下一条边); 车辆
          锁 route → 下一边唯一 → 直行车进 N-T、右转车进 N-R, 即使物理同车道。
          用"车辆意图"而非"所在车道"归类 = B 方案优于纯 lane 方案处 (ABT 设计强调)。
        · 车辆数【不会同时给两个 slot】(用户追问, observations.py __call__
          实测): 聚合循环每辆车调一次 _vehicle_slot → 返回【单一】slot →
          slot_stats[slot]+=1 只加一次。共享车道上 3 直行+2 右转 →
          N-T count=3 / N-R count=2, 相加=5=车道实际车数, 【零重复】。
          count/queue/wait 三个分子量都走此机制。(-1 = 无受控下一跳的车
          被 continue 跳过, 不进任何 slot — 有意。)
        · is_green (准): 该相位放行共享车道时, 它 feed 的所有 slot 都标 served。
        · 容量 (瑕疵): lane_feeds[lane]={N-T,N-R}, cap 累加时这条车道的【完整
          容量被加进它 feed 的每个 slot】→ 同一物理空间在 N-T 与 N-R 的分母里
          被【重复计入】。后果: 共享车道的 slot 容量偏大 → 归一化 density 偏小
          (agent 觉得这些 movement 比实际更空)。

     ★ 瑕疵的精确机制 = 分子/分母口径不一致:
        分子 (count/queue/wait): 按【车辆意图】切分到唯一 slot → 不重复;
        分母 (capacity):         按【车道 feed 的 slot】全额累加  → 重复。
        density = 分子/分母 → 被低估; 瑕疵纯在"分母标度", 不污染车辆动态本身。

     影响有限: 只动归一化标度 (不动 count/queue 相对动态); 仅共享车道发生
     (Dublin 市中心有, 1x3 无 → 1x3 从未暴露); 系统性偏置非噪声, RL 能适应。
     可修 (一行, cap[s] += lcap/len(slots) 均分), 但"共享容量该算给谁"无唯一
     正解 (均分 vs 全额"该 movement 最多排这么长队"各有理)。
     决定 ⭕ 先不改: ① 系统性偏置 RL 可适应; ② Dublin 训练已排队, 改标度会让
     已配实验口径漂移; ③ 该等 Dublin 基线出来、确认共享车道路口策略确实受
     影响再针对性修。列为已知近似。
