  D1 【实质, 新发现】单一需求实现: 训练每个 episode 都用同一
     seed(0) reset (train.py:226/363) 且 routes 文件固定 ⇒ 800 个
     episode 是同一个世界的精确重放; eval 也只有 seed 123 一个实现。
     含义: (a) 策略可能过拟合这一个小时的到达序列; (b) 论文结论目前
     条件于单实现 — 多实现 rou (gen_routes 不同 seed) 的训练扰动与
     eval 是必需项 (与 open item 呼应, 优先级应提高)。
  D2 【实质, 新发现】插入积压不可观测且零成本: 固定配时下
     DepartDelay 已 45s; 被堵在网外的车辆不出现在任何车道上 ⇒ 不进
     state 也不进 reward (等待=0)。理论激励缺口: 把边界进口堵死可以
     "洗掉"这部分等待。当前 boundary 进口多为生成边、policy 难以
     直接利用, 但监控上应加 insertion-backlog 指标, 论文方法节应
     声明该口径。【已落地 2026-06-12: train.py 每 episode 记
     train/pending_veh、每次 eval 记 eval_system/pending_veh
     (episode 末尾的 getPendingVehicles 计数; 仅日志, 零行为影响),
     205-208 起所有 run 自带该指标。】
  D3 【复核后改判: 已有显式决定】teleport 实为禁用 — env.py 默认
     time_to_teleport=-1 并显式传 --time-to-teleport (覆盖 sumocfg)。
     物理纯净、锁死不可逆 — 与 V2 标定 (0 teleports) 和全部 rollout
     观测一致。维持 -1 即可, 无需改动; 唯一残余动作: 论文方法节写明。
  D4 【已验证封口: 非问题, 且窗口有隐藏的正面作用】
     waiting_time_memory=1000 (env.py:102 默认, 经 --waiting-time-
     memory 传 SUMO; 各 config 未覆盖)。
     验证 (ep800 锁死策略 3600s 全程复刻 reward 簿记, 含 3565s 级
     等待): 负差额 0 次、reward>0 步数 0 — 担心的伪正贡献不发生。
     SUMO 语义: 持续等待时 acc 在窗口长度处【饱和】而非回落, 最坏
     只是低计。副发现: 该窗口给 reward 提供了天然下界
     r ≥ −(Σp)·window/awt_scale ≈ −90/步 (实测 ep800 ≈−50/步与之
     一致) — 它本身就是一个弱版 R2。结论: 维持 1000 不改; 若日后
     调大到 3600 会使锁死 reward 加深 ~3.6 倍, 与稳定化方向相悖。
     state 侧: 新 config 的 awt_cap=500 < 1000 先封顶, 窗口无感。
  D5 18 路口共享单网 (forensics P6): 独立网络/独立输出头未对照 —
     ep800 零流量路口 Q 同涨 +1.4e5 是干扰传播实证, 修复属架构臂。
