╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 0: TL;DR                                                              ║
╚══════════════════════════════════════════════════════════════════════════════╝

  B 把每条受控 connection 归入 12 个 movement 槽 (4 方向×3 转向), 每槽
  的 φ = 5 优先级桶 × {count,queue,mean_awt}。聚合规则两条:
    分子 (车辆): 按【路线意图】(route 的下一条边) 归唯一槽;
    分母 (容量): 按【车道 feed 关系】—— 一条车道的 jam 容量加进它
                 feed 的每一个槽。
  判定 (全部有数据):
    ① 多条同向车道 → 同一槽: 【正确】(分子分母同口径相加);
    ② 共享车道的分子: 【正确】(实测 3+6+0=9=车道车数, 零重复);
    ③ 共享车道的分母: 【设计缺陷】—— 分子是意图口径、分母是物理口径,
       两者错配 → density 系统性低估拥堵 (实测: 车道物理占用 0.823,
       agent 看到的最大槽 density 仅 0.549 = 67%);
    ④ 该缺陷在 1x3 不存在 (0 条共享车道), 在 Dublin 普遍 (36 条共享
       车道 / 78 个受影响槽 / 最严重 3 倍低估) —— C5 当时"影响有限"
       的结论对 1x3 成立、对 Dublin 必须修订。
  改进: 简单修法 F1 (容量均分) 被同一份实测数据证伪 (意图偏斜时反向
  高估到 1.646); 正确修法 = I2 "物理占用补充字段" (Part 4)。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 1: 机制 (代码事实, observations.py)                                   ║
╚══════════════════════════════════════════════════════════════════════════════╝

  建表 (_build_movement_tables):
    每条受控 connection → slot=(approach, turn);
    lane_feeds[lane] = 它的 connection 们落入的槽集合;
    cap[slot] = Σ_{lane∈feeds(slot)} lane长度/(MIN_GAP+车长)  ← 注意:
      一条车道若 feed 多个槽, 它的【完整容量】加进每一个槽。
  逐步聚合 (__call__):
    对每辆车: slot = _movement_by_edges[(所在边, route下一边)] —— 意图
    口径, 每车恰好一个槽; count/queue/累计等待按 (slot, 优先级) 累加;
    density 族 = 分子/cap[slot], mean_awt = (Σ等待/count)/100。
  is_green / phase-service: 相位放行该车道 → 它 feed 的所有槽标 served
  (共享车道的多个 movement 同时具备"可放行"信息) —— 正确。
  ψ (outcq) 用同一套槽定义, 在出口侧重复该结构。

╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 2: 情形一 —— 多条同向车道汇入同一 movement: 正确                       ║
╚══════════════════════════════════════════════════════════════════════════════╝

  例 (Dublin meta): 全网 12 个多车道 movement (如双车道直行)。
  分子: 两条车道上意图相同的车都归该槽 → count = 两车道之和;
  分母: cap[slot] = 两条车道容量之和;
  density = 总车数/总容量 —— 分子分母同口径, 无失真。
  这是 movement 粒度的本意 (把"同一冲突流"聚成一个决策对象), 设计正确。

╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 3: 情形二 —— 共享车道: 分子对、分母错 (实测证据)                       ║
╚══════════════════════════════════════════════════════════════════════════════╝

  实测快照 (11h 固定配时, t=181s, Whitefriar 22962979_0:
  82m, jam 容量 10.9 辆, 单车道 feed W-L/W-T/W-R 三个槽):
    车道上 9 辆车, 按意图: W-L 3 辆 / W-T 0 / W-R 6 辆 (含 6 辆排队,
    最长累计等待 31s)。
  ── 分子检验 ✓: 3+0+6 = 9 = 车道实际车数, 每车唯一归槽, 零重复。
  ── 分母失真 (现状, 每槽都用整车道容量 10.9):
       W-L density = 3/10.9 = 0.274
       W-R density = 6/10.9 = 0.549
       物理占用    = 9/10.9 = 0.823
     → 车道实际 82% 满 (近 jam), 但 agent 看到的任何一个槽都不超过
       0.55 —— 拥堵被低估到 67%。根因: 分子是"这个 movement 的需求",
       分母却是"整条车道的存储" —— 口径错配。
  ── 后果: 在共享车道密集的路口 (如 389281, 三个 W 槽全由一条车道
     供给), agent 系统性以为该方向"还很空" → 排绿不足 → 排队进一步
     增长。这与用户在 GUI 观察到的 Whitefriar 长队相互印证 (尽管
     发散主因在训练动力学, 本缺陷在该路口方向上叠加了观测误导)。
  ── Dublin 面: 36 条共享车道 / 78 个受影响槽 / 单车道喂 3 槽的
     低估因子 = 3 (389281, 32236377, 26165126 等)。1x3: 0 条, 无此题。

╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 4: 怎么改 —— 候选修法的逐一数据检验                                   ║
╚══════════════════════════════════════════════════════════════════════════════╝

  F1 容量均分 (cap/len(slots), C5 当时的候选) —— 【被同一快照证伪】:
     W-R density = 6/(10.9/3) = 1.646 (>1, 超 jam!) —— 意图偏向 W-R 时
     反向高估近 2 倍。均分隐含"需求均匀分布"假设, 实测不成立。结论:
     不采用。
  I3 动态份额 (cap × count_s/total) —— 数学上等价于把每个非空槽的
     density 都变成物理占用 (0.823): 失去槽间需求区分 (count 字段仍
     区分, 但 density 全槽同值), 且 count=0 时未定义。次优。
  I2 物理占用补充字段 —— 【推荐】:
     保留现有 count/cap (它的语义是"该 movement 的需求相对车道存储",
     有效) , 另加每槽 1 个字段:
       lane_occ[slot] = max_{lane∈feeds(slot)} (车道上全部车数/该车道容量)
     —— 与意图无关的物理拥堵真值, 有界 (≤~1.2), 共享车道的三个槽
     拿到同一个 0.823 (正确: 它们面对同一份物理拥堵)。
     维度: +12/路口 (每槽 1 标量, 不分优先级桶 — 物理占用无类别);
     实现: _build_movement_tables 已有 lane_feeds, __call__ 一次
     getLastStepVehicleNumber/lane 即可; config 开关 obs_lane_occ
     默认 False (1x3 行为零影响 — 反正 1x3 无共享车道, 开了也只是
     冗余于 count/cap)。
  附带提案 (同属 obs 量级问题, 见 RUN2 文档): F2 mean_awt 封顶/对数
     压缩 — 无界特征在 Dublin 拥堵下达 5-30+, 是发散的输入侧放大器。

  本次 (2026-06-12, 用户批准) 共改 5 个文件, 全部 opt-in:

  ① observations.py (PriorityMovement, 即 B 族):
     新增 include_lane_occ (config 键 obs_lane_occ, 默认 False)
       【目的】修 Part 3 的缺陷: 共享车道上 φ density 的分子是"单个
       movement 的需求"、分母却是"整条车道的存储", 没有任何字段告诉
       agent 这条车道【物理上】有多满 (实测: 车道 82% 满, agent 最多
       看到 0.549)。lane_occ = max(喂入车道的全部车数/该车道容量),
       与转向意图无关, 就是"我面前这条路堵不堵"的真值; 每槽 +1 维。
       不替换原 density —— 原 density 的"需求份额"语义仍有效, 两者
       互补 (需求 vs 物理拥堵)。
     新增 awt_cap (config 键 obs_awt_cap, 默认 None=不封顶)
       【目的】mean/max_awt 是 state 里唯一无界的特征族 (waiting_
       time_memory=1000s → 理论上限 10; Dublin 死锁时大量触顶),
       函数逼近对超出训练分布的输入外推误差最大, 是发散的输入侧
       放大器。封顶值用原始秒数 (如 500), φ 和 ψ 同时生效。
  ② train.py / trainorico.py / traincoeff.py / eval_unified.py:
     各加 2 个 `if key in cfg` 守卫把上述键传进 obs_kwargs。
     【为什么默认关】(a) 不写键 = 字节级原行为 (回归已证: 开关全关
     时 obs 流 sha256 与 git-HEAD 旧代码一致), 已有的 1x3 结论和
     正在引用的实验全部不受影响; (b) 开关式让它们能作为独立对照臂
     被检验, 而不是混进其他改动里无法归因。

╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 7: 两个后续问题 (2026-06-12 用户提出, 数据已测)                        ║
╚══════════════════════════════════════════════════════════════════════════════╝

  Q1. state 的 mean_awt 是 movement 级、reward 是路口级, 有影响吗?
  ────────────────────────────────────────────────────────────────
  粒度不匹配本身【无害且必要】: action 是路口级的, 所以 reward 在
  路口级是对的; state 必须比 reward 细 (agent 要决定先放哪个
  movement, 路口级标量给不了这个信息)。理论上 per-(slot,priority)
  的 count+mean_awt 可以线性重组出路口级 reward —— 细粒度是超集。
  真正的问题在【记账口径】不一致 (本次实测发现):
    reward (priority-avg-waiting, rewards.py:896) 用 env.vehicles
    做了跨车道修正 —— 只算【本车道挣得的等待】;
    state 的 mean_awt 用原始 getAccumulatedWaitingTime —— 车辆
    【全程 (1000s 窗口) 累计】, 包含在上游路口挣的等待。
  实测 (11h, 固定配时, t=600/900/1200 三次采样, 151 辆次):
    继承等待占比: 中位 6.8%, 但均值 35.7% —— 双峰: 47% 的车纯本地,
    34% 的车继承占比 >50%;
    车道级最坏: 3791031#0_0 state 均值 40s vs reward 口径 0s
    (40 倍虚高 —— 上游堵完到这条车道一路绿, state 却显示"久等");
    -554991019_0 (用户曾排查的右转道) 虚高 2.5 倍。
  影响: 下游车道的 mean_awt 被上游拥堵污染 → agent 对"该 slot 的
  服务紧迫度"校准错误 + TD 目标噪声。
  【勘误 2026-06-12】本节初版写"1x3 行程短、不影响" —— 实测证伪:
  1x3 同口径诊断 (固定配时, 385 辆次): 继承占比中位 20.5%, 均值
  40.4%, >50% 的车 36.6% —— 与 Dublin (均值 35.7%) 同量级。走廊型
  路网里 W↔E 车流连过 3 个口, 继承一点不少。
  覆盖面 (代码确认): A/T 共用 _lane_bucket_stats (L405), B 的 φ
  (L748) 和 ψ (L803) —— A/B/T 全部是全程口径; reward 全部是本路口
  口径。即三族 state 与 reward 口径全线不一致。
  对既有结论的影响判定:
    - 不污染 reward/训练数据本身; 1x3 各 arm (A/B/T/coeff/colight/
      nocoord, ±ψ) 全部同口径 → arm 间【比较】仍内部有效;
    - 不是 Dublin 发散的主因 (同口径下 1x3 colight 教科书式收敛;
      发散指纹是 Q 自举膨胀, 见 RUN2 Part 3);
    - 但所有 arm 的 mean_awt 信息质量都被打折 (~1/3 车辆的紧迫度
      信号被上游污染), 等于全体损失了一截天花板。
  修法 (设计待批): obs_awt_basis = "global"(默认, 原行为) | "local"。
  local 实现: 首次见到 (vid,lane) 时记 entry_acc, 本地等待 =
  acc - entry_acc (过路口等效清零) —— 自包含, 不依赖 reward 的
  env.vehicles 簿记 (queue 系 reward 不维护它, 不能复用)。
  A/T 改 _lane_bucket_stats、B 改 φ/ψ 两个循环, 一个开关全覆盖。
  论文策略是用户的设计决定: (i) Dublin 重启时作为对照臂;
  (ii) 若定 local 为新标准, 1x3 关键 arm 需重跑; (iii) 或保留
  global 并在论文里给"累计受苦"的公平性解释 (有文献辩护空间,
  但与 reward 口径不对偶, 设计故事变弱)。

  【用户假设检验 (2026-06-12 续): "1x3 能 work 是因为 bus 不累计、
   car/amb 行程可控; Dublin 上 global 口径导致训练分布问题"】
  四个可测推论, 全部实测:
  ① "bus 没有累计" ✓ 字面成立: 1x3 的 bus 全部 NS 直行, 每辆恰好
     过 1 个信号路口 (rou 注释+静态统计), bus 桶 mean_awt 天然纯
     本地; Dublin bus 中位过 2 个、P90 过 7 个路口 (GTFS 真路线)。
     特征上: bus 桶 global P99 — 1x3 ≈0.19, Dublin →1.96 (10 倍),
     而 bus 在 531 权重里是 3, 污染恰好落在 reward 最重的桶上。
  ② "car 行程可控" ✓: 1x3 走廊 car 过 3 口但畅通, global P99 全程
     平稳 (1.98→1.94→1.81→1.57, 无趋势); Dublin car 中位 1 但
     P90=3, max=11。
  ③ "amb 可控" ✓: 1x3 amb 单条固定路线 3 口、3.5 辆/h; Dublin
     中位 3, max 6。
  ④ "训练分布差太大" ✓ 但机制要精确化 —— 不是"没见过", 是【非平稳
     漂移】: 同一小时固定配时内, Dublin 的 global mean_awt P99 从
     1.58 漂到 5.09 (3.2 倍, 还在向 memory 上限 10 走), 而 local
     口径同一仿真同一需求下 P99 始终有界 (0.87–1.78, 无趋势);
     1x3 的 global 口径本身就平稳。即: global 口径把"全网拥堵史"
     注入每个路口的 state → 输入分布随时间/随策略变化而漂移,
     策略越差特征越大 (反馈环), 函数逼近的外推误差被持续喂大 ——
     这正好接在 deadly triad 的"函数逼近"腿上。
  判定更新: 训练动力学仍是发散的【引擎】(±clip、exp199 证据链
  不变), 但 global-awt 漂移是 Dublin 比 1x3 难得多的【obs 侧主
  机制】—— 1x3 上 global≈无害 (平稳+高优先桶干净, 既有结论无需
  重跑), Dublin 上 obs_awt_basis=local 应从"触发器待办"升级为
  【重启训练包的核心成员】(与 Double/慢目标/Huber 同捆)。

  Q2. 进出道路有长有短, 要不要限制 state 统计范围?
  ────────────────────────────────────────────────────────────────
  数据 (dublin_8std net, 18 TLS):
    进车道长度: 10–373m, 中位 77m; >150m 的 10/65, <30m 的 11/65;
    同一路口内最大悬殊 10 倍 (389281: 11m vs 106m;
    cluster_21620852…: 43m vs 373m)。1x3 对照: 全部 173–186m, 均匀。
  三个真实效应:
    (a) 同路口内 slot 间不可比 —— density 分母=车道容量, 同样 8 辆
        排队在 373m 道上读 0.16、在 30m 道上读 2.0 (截断后 1.0+):
        agent 的核心决策恰恰是 slot 间比较, 这是直接失真;
        (lane_occ 同样有此长度依赖, I2 不解决 Q2);
    (b) 短车道 (11 条 <30m, 最短 11m≈1.5 辆) 瞬间饱和→density 钉在
        jam, 梯度信息消失; 且排队溢出到上游边后 state 完全看不见
        (统计范围=本车道) —— 限程修不了这个, 要往上游扩展才行;
    (c) 长车道把 350m 外的自由流车辆计入 count —— 对 5s 级决策是
        噪声 (但 queue/mean_awt 天然只在停车处累积, 受影响小)。
    reward 不受长度影响 (等待发生在哪都是真等待), 无需动。
