╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 1: outgoing 到底是什么信号 — 单路口 vs 多路口的角色转变               ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 1.1 单路口: 可放行性 (dischargeability) ─────────────────────────────────
    给某方向绿灯的前提是"放出去的车有地方去"。出口被占满 → 绿灯放不动车
    (spillback 堵口), 绿时纯浪费, 极端时锁死路口。outgoing 占用率是这个
    约束的唯一直接观测。
    但在 1x1 syc: 所有出口都是边界边, 车辆直接离网 → occupancy 永远≈0,
    该信号是常量。✓ 这就是 1x1 不加的全部理由 — 不是设计取舍, 是物理事实。

  ── 1.2 多路口: 同一条链路, 两个角色 (本文最重要的观察) ─────────────────────
    1x3 里 t 的东出口车道 == e 的西进口车道 — 同一段物理车道:
      对 t (上游): 它是"我的下游容量约束" → ψ 视角, type-agnostic
      对 e (下游): 它是"我的到达需求"     → φ 视角, 按优先级分桶
    同一数据、两个路口、两种特征化 — 不是冗余, 是两个不同决策各自需要的
    投影。这同时回答了"会不会重复计入": 会, 而且应该 — t 用它决定"还要不要
    往里灌", e 用它决定"该不该放行"。

  ── 1.3 ψ 的领先性: 为什么它能改善 credit assignment ───────────────────────
    spillback 链: J0 堵 → e→J0 链路渐满 → e 的 ψ 变大 (e 提前看见) →
    e 计量进流 → t→e 链路渐满 → t 的 ψ 变大。
    没有 ψ 时, "往堵处灌绿灯"的恶果只能通过 N 步后的 reward 回传 — 信用
    分配链长、学得慢; 有 ψ 时, 恶果在 t+1 的 obs 里就可见 (出口占用率上升),
    Q 函数能直接建立 "ψ 高 + 给该方向绿 → 坏" 的短链关联。
    对 200m 链路 / 5s 决策粒度, ψ 比"恶果以本路口排队形式折返"提前约一个
    链路填充时间 — 这是它"好训练"的机制性理由。
    [推测] 该领先性在高需求时段最值钱 (链路接近容量时), 低需求时 ψ≈0 无害。

  ── 1.4 成本: ψ 比 φ 还便宜 ─────────────────────────────────────────────────
    φ 要逐车 getTypeID/速度/等待 (per-vehicle TraCI); ψ 只要每出口车道两个
    聚合量 (getLastStepVehicleNumber / getLastStepHaltingNumber), 无逐车
    迭代、无类型查询。维度: A +2K, B +2×槽数, T 每 token +2 — 全部可忽略。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 2: 为什么容量侧 type-agnostic — "优先级住在需求侧"原则                ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 2.1 出口车辆的控制无关性 ────────────────────────────────────────────────
    已驶入出口链路的车, 本路口的任何动作都不再影响它 — 它的类型 (amb/bus/car)
    对本路口的决策没有信息量。本路口只关心一件事: 那条链路还装得下几辆。
    "装得下几辆"与车型无关 → ψ type-agnostic。
    (对照: PriorityBCA 的 out 块是 per-type 计数 — 维度 ×3 换不来控制信息,
     这是历史设计的冗余, 不是要继承的特性。)

  ── 2.2 "救护车绿波需要 per-type out" 是误解 — 多路口下天然不需要 ────────────
    直觉: "下游该提前知道救护车要来 → 上游的 out 块要标 amb"。
    实际: 在多路口拓扑里, 上游的出口链路 == 下游的进口车道 (1.2), 而下游的
    进口 φ 本来就按优先级分桶 — 救护车一驶入链路, 下游路口的 φ_p5 立刻点亮
    (syc 链路 150-200m, 提前 ~10-20s 可见)。绿波的"提前知道"由接收方的
    incoming φ 天然实现, 不需要发送方的 outgoing 重复携带。
    → 需要更早预警 (2-hop) 时, 正确工具是协同层 (邻居 obs / GAT / 事件门控
      reward), 不是把 ψ 复杂化。各层各司其职。

  ── 2.3 原则定型 (写进设计不变量) ───────────────────────────────────────────
    I6: 需求侧按优先级分桶 (φ, 5级×字段), 容量侧车型无关 (ψ, 2 标量)。
        优先级是"谁先走"的语义, 只对还没走的车有意义。
    这个不对称本身就是 contribution 的一部分: 比"in/out 全 per-type"
    (PriorityBCA) 更省、比"无 out" (当前 A/B/T) 更全, 且每一维都有控制语义。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 3: ψ featurizer 定义 + 三方案挂法                                     ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 3.1 ψ 定义 ──────────────────────────────────────────────────────────────
    对一组出口车道 L_out:
      ψ(L_out) = [ Σcount / Σcap,  Σhalting / Σcap ]        (2 维, 默认)
      可选第 3 维: max_lane_occ = max_l (count_l/cap_l)      (spillback 旗标:
        多车道出口里只要一条满就堵该 movement; 聚合均值会掩盖它)
    归一化口径与 φ 相同 (jam 容量 = length/(MIN_GAP+车长), 不变量 I5)。

  ── 3.2 A (相位级): 每相位行 + ψ(该相位出口集) ──────────────────────────────
    出口集 = 该相位 G/g 连接的全部 to-lanes (getControlledLinks 按
    phase.state 索引, 与 incoming 的 _build_phase_served_lanes 同构)。
    注意: 常绿右转的 to-lanes 会进所有相位的出口集 — 与 incoming 侧的
    重复计入完全对称, 同一取舍同一文档化, 不特殊处理。
    维度: legacy cq 45 → 45+4×2 = 53。

  ── 3.3 B (转向级): 每槽 + ψ(该 movement 的 to-lanes) ───────────────────────
    movement→to-lanes 是连接级一一定义 (建 _link_slot 时顺手缓存), 三方案中
    映射最干净 — 出口语义本来就是 movement 的属性。共享出口车道 (两个
    movement 汇入同一条出口) 各自计入各自的 ψ — 正确: 两个 movement 面对
    同一个容量约束。
    维度: legacy cq 125 → 125+12×2 = 149。

  ── 3.4 T (车道 token): 每进口 token + ψ(该车道连接喂向的出口聚合) ───────────
    推荐方案 (i): token = [is_green?][service K][φ][ψ 2] — token 数不变,
      token_dim 14→16 (legacy cq+svc), obs 173→197。
    备选方案 (ii) "出口也当 token": 概念上更对称, 但 (a) 出口 token 的
      service 位无意义 (没有相位"放绿"一条出口), 需要 role 位 + 语义分叉;
      (b) 它真正的价值在"网络级 Transformer"— t 的出口 token 与 e 的进口
      token 是同一条车道, 是跨路口图注意力的天然缝合点。→ 方案(ii) 留给
      Stage 3+ 的网络级架构, 单路口 agent 阶段用 (i)。
    token_layout 契约同步: token_dim 公式 + assert 自动随 fields/ψ 开关走。

  ── 3.5 开关与适用规则 ──────────────────────────────────────────────────────
    include_downstream (默认 False) — 与 include_phase_service 同风格的
    构造参数 + config 键。适用判据: 场景存在"内部出口" (出口边是其它受控
    路口的进口边) 才值得开; 纯边界出口 (1x1) 开了也只是常量维。
    边界出口不需要特判 — 它们的 ψ≈0 恒定, 网络自会忽略; 规则只决定
    "要不要开这个 flag", 不增加代码分支。


╔══════════════════════════════════════════════════════════════════════════════╗
║   Part 4: 多路口专题 — ψ 在协同阶梯中的位置                                  ║
╚══════════════════════════════════════════════════════════════════════════════╝

  ── 4.1 协同阶梯 (信息量递增, 通信成本递增) ─────────────────────────────────
    L0  无协同:        只看自己 incoming (当前 A/B/T)
    L0.5 ψ (本文):     看自己出口链路占用 — 0 通信, 本地可观测,
                       "邻居最近的控制后果"被动地写在共享链路上
    L1  邻居 obs 拼接:  看邻居完整 state (CoeffDQN 的 concat 部分)
    L1' GAT 注意力:     L1 + 学习"听谁多少" (CoLight)
    L2  reward 层:      邻居 reward 进 TD target (CoeffDQN β / 事件门控)
    实测背景 (COORDINATION doc): 1x3 上 L1/L1' 把 bus 压到 2.3 (vanilla 5.1),
    但同时是倒挂放大器。ψ 是这架梯子上最便宜的一级 — 多路口实验的核心问题
    因此变成: **协同收益沿梯子怎么分布? 爬到哪一级拿到多少?**

  ── 4.2 判别实验 E1b: ±ψ 因子 ───────────────────────────────────────────────
    设计: 1x3, E1 胜者状态方案 × {ψ 关, ψ 开} × (可选 ×{±stratified})。
    判定: system/bus/car 效率, amb 指标, 以及与 CoLight (L1') 的差距占比:
      gain_ratio = (vanilla+ψ 相对 vanilla 的改善) / (CoLight 相对 vanilla 的改善)
    [推测] 三种结局, 各自的论文叙事:
      gain_ratio 大 (>0.5): "所谓协同收益, 大半只是看见下游堵了" —
        被动可观测性 > 主动通信, 对协同文献是有力的简化性结论;
      gain_ratio 小 (<0.2): 主动协同的增量价值被坐实, CoLight 的 attention
        确实在做 ψ 给不了的事 (如绿波相位锁相);
      中间: 阶梯逐级递减收益 — 也是干净的刻画。
    无论落在哪格, E1b 都产出结论 — 这是好实验的标志。

  ── 4.3 ψ 与倒挂的关系 — 诚实的预测 ────────────────────────────────────────
    [推测] ψ 可能轻度加深 5-4-1 倒挂: 既有实测规律是"优化能力越强, 倒挂
    越狠" (容量、协同两轴三重确认), ψ 提升走廊效率 → 给优化器更多"压 bus
    等待"的空间 → 同一机制。但 ψ 不针对类别, 不直接挤占 amb 相位 —
    预计效应弱于 L1 协同。
    处置不变: 倒挂靠排序层解决 (PRIORITY_ORDERING 的 G1/Y1), 不靠扣掉
    有用的状态信息。"为了不倒挂而让 agent 看不见下游"是错误的修法。

  ── 4.4 与 MaxPressure/PressLight 的对接 (文献定位) ─────────────────────────
    MaxPressure: phase 压力 = Σ(上游队列 − 下游队列), 固定差分, 网络级
    吞吐最优性证明的来源正是下游项。本设计 = "可学习的 pressure 超集":
    φ(按优先级的上游) + ψ(无类型的下游) 喂给 Q, 差分关系可学、可超越
    (e.g. 非线性 spillback 阈值)。论文里这是一段现成的 related-work 定位:
    PressLight 用 in/out 车数, 我们用 priority-bucketed in + capacity-only
    out — 每一步偏离都有控制语义理由 (Part 2)。
